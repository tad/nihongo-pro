# Nihongo Pro — context for Claude

Personal Japanese-study iPadOS app. SwiftUI, iPadOS 26+ only, single target, zero third-party dependencies.

## Visual identity

- **Palette** (defined in `NihongoPro/Assets.xcassets/`):
  - `AccentColor` — deep indigo (kon-iro), light `#2A3A6B`, dark `#7BA0E0`. Used everywhere SwiftUI reads `.tint` / `.accentColor`.
  - `PaperBackground` — warm cream / off-black. Light `#FFFCF5`, dark `#1A1814`. Applied as `Color.paperBackground.ignoresSafeArea()` behind the main screen and the two modals. Auto-generated by Xcode's asset symbol generation (`ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS = YES`), so the property name is `paperBackground` (camelCased from the asset name), not the asset filename.
  - `Vermillion` — warm red-orange (shu-iro), light `#DC4F35`, dark `#F1715A`. Reserved as a celebratory accent — currently used for "Known" indicators in `StatsView` (summary cards + `LevelDot` + the Known segment of the `DistributionBar`). Not used for primary buttons (those stay indigo accent).
  - `.orange` / `.red` keep their semantic roles (warning / destructive). Orange also drives the pomodoro break overlay scrim and the "on break" tint of `PomodoroPill`.
- **Card chrome** — `cardChrome(cornerRadius:padding:)` View extension in `NihongoPro/Theme.swift`. Applies `.padding`, `.regularMaterial` rounded background, and a soft shadow (`black.opacity(0.06)`, radius 12, y 2). Used on: the parsed-sentence card on the main screen, the top word-header card in `WordDefinitionView`, and the Words / Kanji sections in `StatsView`.
- **Typography tokens** in `Theme.swift`: `Font.displayKanji` (96pt serif), `Font.displayWord` (72pt serif), `Font.sentenceLarge` (32pt serif). Used across `KanjiDetailView` and `WordDefinitionView` to keep the recurring large display sizes consistent.
- **Motion** — Break overlay scale-fades in via spring. `PomodoroPill`'s seconds use `.contentTransition(.numericText())` so digits tick rather than snap; icon swaps use `.symbolEffect(.replace)`. The `TextEditor` on the main screen animates its border tint when focus changes (`.smooth(duration: 0.2)`).

## Architecture (locked-in decisions)

- **Multi-pass translation:** pasting/typing into the input area kicks off two sequential Anthropic Messages calls (`claude-sonnet-4-6`, plain `URLSession`) after a debounce. A third on-demand call powers the Breakdown view.
  - **Auto-parse on input change:** `ContentView.handleInputChange()` (wired via `.onChange(of: inputText)`) cancels any in-flight `autoParseTask`, resets parsed state if the text differs from `parsedInputText`, and — when the input is non-empty, single-sentence, and an API key is present — schedules a debounced `Task` that sleeps 800ms then calls `translate()`. The English translation is fetched in the same call but stays hidden until the user reveals it (see below). `translate()` captures the trimmed input at start and bails (without setting state) if `inputText` has changed by the time the network result returns, so racing pastes can't corrupt the display.
  - **Translation reveal:** `isTranslationRevealed` gates whether the translations are shown. The reveal renders **two** stacked, captioned blocks via `ContentView.translationBlock` / `labeledTranslation(_:_:)`: a `LITERAL` block (the grammar-following `literalTranslation`) above a `NATURAL` block (the fluent `englishTranslation`). Both use the same 32pt-ish title2 secondary style; the small uppercase `.caption2` tertiary captions are what distinguish them. The literal block is omitted when `literalTranslation` is empty (model didn't return one, or a pre-feature saved sentence was reloaded). The "Show translation" button only renders once `words` and `englishTranslation` are populated (i.e., the auto-parse has completed) — there is no impatient-user pathway; the user always sees the Japanese first, then the button appears. Tapping it simply flips `isTranslationRevealed = true`. The Breakdown button only appears post-reveal. `parsedInputText` tracks which input the current `words` / translations belong to so reveals never show a stale translation. `translationBlock` is shared by the reveal and the Breakdown header so the literal/natural pair appears identically in both.
  - **Literal translation:** a more literal, grammar-following English rendering (style: readable English that preserves Japanese word/phrase order — topic first, verb/copula last — and conveys particle function through phrasing like "as for X" / "(I)" rather than bracketed glosses; **no** interlinear notation or romaji). It rides along in **Pass 1** (a third `literal_translation` JSON field — no extra API call), decoded into `TranslationResult.literalTranslation` (defaults to "" if absent — defensive). Held behind the same reveal gate as the natural translation. Baked into `SavedSentence.literalTranslation` (optional, so old saved files decode). Tune its style in `translationSystemPrompt` (the `literal_translation` field guidance + worked example).
  - **Pass 1 — `TranslationService.translate(_:)`:** returns `{words: [{text, reading, furigana, tts_kana}], translation, literal_translation}`. No definitions. `tts_kana` is a per-word boolean (decoded into optional `Word.ttsKana`, absent ⇒ `false`) that Claude sets `true` only for words whose kanji reading is uncommon/non-obvious enough that a TTS engine would mis-read it (rare/technical compounds like 精米歩合, unusual name readings, ateji/gikun). It drives selective kana substitution for sentence speech — see the speech-input note below. Words/furigana are displayed and the sentence is spoken as soon as it lands so the user can read/hear the sentence; the translation is held back behind the reveal gate. On `.invalidResponseFormat`, `translate(_:)` retries once with the input passed through `sanitizeForJSON(_:)` — which **strips** all quote-like characters entirely (ASCII `"`/`'`, U+201C/D smart double, U+2018/19 smart single, U+201E/A/F low quotes, U+2032/33 primes, U+00AB/BB guillemets, U+301D-F double-prime quotation) and replaces ASCII `\` with `／` (U+FF0F). The original failing input was a sake brewery description containing mixed quote variants; even after replacing them with typographic quotes Claude still produced invalid JSON, so the retry path now drops quote chars entirely as the most reliable recovery. Fidelity tradeoff: quote characters disappear from the output on the retry path, but the sentence parses. `max_tokens` is 8192 here to leave headroom for long sentences with 20+ word entries. JSON extraction (`Self.extractJSON`) is permissive: it strips code fences AND slices from the first `{` to the last `}` so any stray prose around the JSON doesn't break the decode. Parse-failure errors surface (a) detailed `DecodingError` info — `dataCorrupted` unwraps the underlying `NSError`'s `NSDebugDescription`; `keyNotFound`/`typeMismatch`/`valueNotFound` include the coding path — and (b) a generous `previewSnippet` of the raw response (600 head + 600 tail with middle elided), so future failures are diagnosable from the in-app error banner alone.
  - **Pass 2 — `TranslationService.fetchDefinitions(sentence:words:)`:** sends `{sentence, words: [...]}` and gets back `{definitions: [String?]}` aligned to the words by index. `ContentView` merges the array into the existing `words` state (`Word.definition` is `var`). A subtle "Loading word definitions…" indicator appears below the English translation while pass 2 runs; on failure it becomes a "Couldn't load definitions" message with a Retry button.
  - **On-demand — `TranslationService.fetchBreakdown(sentence:words:translation:)`:** fired only when the user taps the Breakdown button. Sends the sentence, the per-word data (including any definitions from pass 2), and the English translation; gets back Markdown with these sections in order: `## Vocabulary`, `## Grammar`, `## Sentence structure`, `## Notes` (the prose commentary). `ContentView.breakdownContent` renders the shared `translationBlock` (literal + natural translations) **above** the `BreakdownView` so the reader sees the meaning, then the structural breakdown, then the Notes paragraph at the bottom. (Note: only the *natural* `translation` is sent to `fetchBreakdown` — the literal rendering is display-only and not part of the breakdown request payload.) The Markdown is cached in `ContentView.breakdown` for the current translation and survives toggling.
  - Four system prompts pinned in `TranslationService.swift` (`translationSystemPrompt`, `definitionsSystemPrompt`, `kanjiInfoSystemPrompt`, `breakdownSystemPrompt`) — each includes a worked example to lock in output shape. All four Anthropic calls go through a shared private `sendMessage(systemPrompt:userMessage:maxTokens:)` helper.
- **Tap-to-define:** every word in the Japanese display is a `Button` in `FuriganaText`, disabled while `definition == nil`. The 1.5pt accent underline that marks a word as tappable is also gated on `definition != nil`, so it only appears after pass 2 lands. Tapping a tappable word opens `WordDefinitionView` as a medium-detent sheet showing the word, kana reading, English definition, and a speaker/stop button that plays just that word using the shared `SpeechService`.
- **Tap-to-explore-kanji:** inside `WordDefinitionView`, the large word header is rendered character-by-character. Kanji characters (CJK Unified Ideographs — `Character.isKanji`) become tinted, underlined `Button`s; hiragana/katakana/punctuation render as plain `Text`. Tapping a kanji presents `KanjiDetailView` as a nested medium-detent sheet showing the character, English meanings, on'yomi/kun'yomi readings, a memorable note (all from a Claude call `TranslationService.fetchKanjiInfo(kanji:)`), and a natively-rendered animated stroke order via `KanjiStrokeView`. Stroke data comes from `KanjiVGService.loadSVG(for:)`, which fetches from KanjiVG (`raw.githubusercontent.com/KanjiVG/kanjivg/master/kanji/{codepoint}.svg`) on first request and caches the SVG to the app's `cachesDirectory` for offline reuse. KanjiVG is CC BY-SA 3.0 and the attribution is shown inside `KanjiDetailView`.
- **Pomodoro study timer (`StudySession`):** the "Start study" button at the bottom-right of the action row — visible once a sentence is parsed and definitions have loaded, hidden while a session is already running — instantiates a parameterless `StudySession` (`@MainActor @Observable`, `Identifiable`) and stores it in `ContentView.studySession`. There is no full-screen cover and no per-sentence content tied to the session; the pomodoro runs alongside the regular `ContentView` so the sentence, word/kanji modals, and Breakdown stay fully interactive while studying. A **single** 25-min work / 5-min break cycle runs (it does NOT loop into a new work block): a `Task` polls every 500ms against a wall-clock end date; when the work timer expires the session plays the chime and switches into break mode (orange `breakOverlay` rendered as a `ZStack` sibling above the main `VStack`, locking the UI until the 5-min break ends). When the **break** timer expires, `finishSession()` cancels the timer and sets `isFinished = true`; `ContentView` observes this via `.onChange(of: studySession?.isFinished)` and clears `studySession` (dismissing the pill + overlay). The Task is `[weak self]`-guarded so it self-terminates when the session deinits — no explicit `deinit` needed. **Chime:** `playChime(remaining:)` plays system sound `1005` (the longer "alarm" tone) `chimeRepeats` (3) times back-to-back via `AudioServicesPlaySystemSoundWithCompletion` completion-chaining so the tones don't overlap and the end-of-work block is hard to miss. System-sound volume tracks the device ringer/system volume and can't be boosted programmatically. While a session is active, `ContentView` adds two `topBarTrailing` toolbar items to the left of the existing stats/gear buttons: `PomodoroPill` (declared at the bottom of `ContentView.swift`) showing `timer`/`moon.fill` + `monospacedDigit` time with `.contentTransition(.numericText())`, and an `xmark.circle.fill` End Session button that fires `showingEndSessionConfirmation` → destructive "End session?" alert → `session.end()` + `studySession = nil`.
- **Familiarity levels (`FamiliarityStore`):** `@MainActor @Observable` singleton (`FamiliarityStore.shared`) tracking a three-tier self-rating per word and per kanji: `.unknown` (default, absent from dict), `.familiar` (stepping stone — purely informational, behaves the same as Unknown), `.known` (graduated — hides furigana). Two JSON files in `applicationSupportDirectory/NihongoPro/`: `word_familiarity.json` (`[String: Level]`, keyed by `Word.text`) and `kanji_familiarity.json` (`[String: Level]`, keyed by `String(Character)`). Loaded into memory in the init via the same `try? Data(contentsOf:)` + `try? JSONDecoder().decode(...)` pattern as `DefinitionCache`. Setting a level to `.unknown` removes the entry from the dict so files only grow with user-marked items. Writes are dispatched via `Task.detached` (atomic write) so the main thread never blocks. Diverges from the `actor`-pattern used by `DefinitionCache`/`FrequencyTracker` because the store is read synchronously inside SwiftUI view bodies and changes must drive UI updates reactively — `@Observable` macro tracks the dict accesses for free.
  - **UI:** segmented `Picker` (Unknown / Familiar / Known) provided by two reusable views in `FamiliarityStore.swift`: `WordFamiliarityPicker(word:onKnown:)` and `KanjiFamiliarityPicker(kanji:onKnown:)`. Both write to the store via a `Binding`; if the user sets the level to `.known`, the optional `onKnown` closure fires (dispatched via `Task { @MainActor in onKnown() }` so it runs after the binding-set completes, not mid-SwiftUI-state-mutation). Used in `WordDefinitionView` (near "Seen N times", above the word header) and `KanjiDetailView` (between "Seen N times" and the kanji glyph). No `onKnown` is passed at either site — the level is set, the modal stays open. No `.task` loader needed; the store is in-memory by the time the modal appears.
  - **Furigana suppression:** `FuriganaText.shouldHideFurigana(for:store:)` returns `true` if (a) the word itself is `.known`, OR (b) the word contains at least one kanji and **every** kanji char in `word.text` is `.known`. `WordView`'s effective `hideFurigana` is `!showFurigana || shouldHideFurigana(...)` — the global furigana toggle (see below) flips it off by default, and the Known-word check still wins when the toggle is on. The boolean gates the ruby `Text(...).opacity((hideFurigana || seg.reading == nil) ? 0 : 1)` — opacity (not conditional render) preserves the row's vertical layout regardless of state. The 1.5pt accent underline and the wrapping `Button` are untouched.
- **Global furigana toggle:** furigana is **off by default**. `ContentView` owns a `@AppStorage("showFurigana") var showFurigana: Bool = false` and threads it into `FuriganaText` via the `showFurigana:` parameter (defaults to `false` if not passed). A toolbar button in `topBarTrailing` (just left of the library button) toggles it — `character.book.closed.fill` filled+accent when on, `character.book.closed` outlined+secondary when off, with a `.symbolEffect(.replace)` swap animation. Setting is persisted to `UserDefaults` and survives relaunches. Known words still hide furigana even when the toggle is on (the per-word suppression rule above wins). The button is `.disabled` while reading-drill mode is active (drill forces furigana off).
- **Reading drill mode:** `ContentView` owns `@State drillMode: Bool` toggled by a `graduationcap`/`graduationcap.fill` toolbar button (leftmost of the trailing group, before the furigana toggle). It's threaded into `FuriganaText` via the new `drillMode:` parameter. In drill mode **all** furigana is hidden regardless of `showFurigana`, and tapping a word reveals just its reading inline (instead of opening `WordDefinitionView`). `FuriganaText` branches on `drillMode`: the drill path wraps each word in a `Button` whose action toggles the index in a `@State revealedIndices: Set<Int>`, with `WordView(hideFurigana: !revealed, underline: revealable)`; the normal path is unchanged (tap → `onWordTap`, underline gated on `definition != nil`). A word is *revealable* (`Self.hasReading`) iff it has any furigana segment with a non-nil reading — pure-kana words have nothing to test and are `.disabled`. `revealedIndices` is reset via `.onChange(of: words.map(\.text).joined())` so reveals never leak across sentences. `WordView` gained an explicit `underline: Bool` parameter (was previously computed internally from `definition != nil`) so the two call paths control the tappable-underline independently.
- **Exposure counters (`FrequencyTracker`):** actor singleton (`FrequencyTracker.shared`) tracking how many times each word (surface form) and each individual kanji has appeared in a successfully parsed sentence. Two JSON files in `applicationSupportDirectory/NihongoPro/`: `word_frequencies.json` and `kanji_frequencies.json` (both `[String: Int]`). `recordSentence(words:)` is called from `ContentView.translate()` immediately after `words = result.words` — it iterates the words and, **for each word where `JapaneseWordFilter.shouldCount(_:)` returns true**, increments the word count and (for each kanji `Character` in the word) the kanji count. Pure punctuation and common grammatical particles are filtered out entirely — they bloated the data without adding study value. Single batch write per file per parse (not per increment). `WordDefinitionView` and `KanjiDetailView` each read their respective count in a `.task` modifier on appear and render `"Seen N times"` (or `"Seen 1 time"`) as a small `.caption .secondary` label at the top-left of the modal **only when the count is > 0** — opening the modal for a particle (which now has count 0) hides the label entirely rather than showing a misleading "Seen 0 times". The current parse counts for tracked words, so a tracked-word modal you just opened never shows 0. Pasting the same sentence twice = +2 (intentional — counts exposures, not unique sentences). On init, the actor scrubs any pre-existing punctuation/particle entries from `wordCounts` (one-shot migration on every launch; idempotent once clean; the persist inside init is inlined rather than calling the actor-isolated `persistWordCounts()` to keep Swift 6 isolation rules happy). `snapshot() -> (words: [String: Int], kanji: [String: Int])` returns both dicts at once — used by `StatsView` to drive the Progress sheet.
- **Shared filter (`JapaneseWordFilter`):** top-level enum declared at the top of `FrequencyTracker.swift` (placed there to avoid a new pbxproj file). Exposes `commonParticles: Set<String>`, `isPurePunctuation(_:)` (CharacterSet of `.punctuationCharacters` ∪ `.whitespacesAndNewlines`), and `shouldCount(_:)` (the conjunction). Used by `FrequencyTracker.recordSentence` (track filter), `FrequencyTracker.init` (scrub filter), and `TranslationService.fetchDefinitions` (cache routing — skip Claude calls for pure punctuation). Previously each call site had its own private copy of these checks; centralising avoids drift if we ever tune the particle list.
- **Daily activity (`ActivityTracker`):** `@MainActor @Observable` singleton (`ActivityTracker.shared`) tracking how many sentences were parsed and how many pomodoro work blocks were completed each calendar day. Two JSON files in `applicationSupportDirectory/NihongoPro/`: `daily_activity.json` (parses) and `daily_sessions.json` (completed study sessions), both `[String: Int]` keyed `yyyy-MM-dd` in the user's current calendar/timezone via a cached `en_US_POSIX` `DateFormatter`. `recordParse(on:)` is called from `ContentView.translate()` right after `FrequencyTracker.recordSentence` and increments today's parse count. `recordStudySession(on:)` is called from `StudySession.startBreakInterval()` — i.e. the moment a 25-minute work block completes (the work→break transition), so a session counts once even if the user cuts the break short, and a session aborted *during* the work block never counts. Writes are dispatched via `Task.detached` (atomic). `@MainActor @Observable` (not the `actor` pattern) because `StatsView` reads it synchronously in its body. Computed helpers drive the Progress sheet: `todayCount`, `daysStudied` (count of days with ≥1 parse), `currentStreak` (consecutive days ending today — or yesterday if today has no activity yet, so an as-yet-unstudied day doesn't break the streak), `recentDays(_:) -> [(date, count)]` (oldest-first window for the bar chart), `totalStudySessions` (all-time sum), and `todayStudySessions`.
- **Saved sentences (`SavedSentenceStore` + `LibraryView`):** `@MainActor @Observable` singleton (`SavedSentenceStore.shared`) persisting bookmarked sentences to `applicationSupportDirectory/NihongoPro/saved_sentences.json` (array of `SavedSentence`, newest-first; writes via `Task.detached` atomic). `SavedSentence` is `Codable, Identifiable` = `{id, text, words: [Word], englishTranslation, literalTranslation: String?, savedAt}` — the **full parse is baked in** (furigana + per-word definitions + both translations, since `Word` is `Codable`) so a saved sentence reopens instantly and offline. `literalTranslation` is **optional** specifically so saved files written before the literal-translation feature still decode (older records just have no literal block). Identity is the surface `text`: `save` de-dupes by removing any existing same-text entry first; `isSaved`/`remove`/`toggle` all key on trimmed text. **UI:** a `bookmark`/`bookmark.fill` button sits in a `VStack` with the speaker button on the trailing edge of the parsed-sentence card (`ContentView.toggleSaved()`, gated on `!words.isEmpty && !englishTranslation.isEmpty`, reads `isCurrentSentenceSaved` which checks the store against `parsedInputText`). A `books.vertical` toolbar button (between the furigana toggle and the stats button) presents `LibraryView` — a `NavigationStack`+`List` (paper background, `.scrollContentBackground(.hidden)`) of saved sentences showing the Japanese (serif), translation snippet, and relative save date, with swipe-to-delete and tap-to-load. Tapping calls back into `ContentView.load(_:)`, which sets `words`/`englishTranslation`/`literalTranslation`/`parsedInputText` and finally `inputText` — crucially `parsedInputText` is set **before** `inputText` so the `onChange` auto-parse handler sees them equal and bails (no network re-parse), reusing the saved parse as-is. `isTranslationRevealed` is reset to `false` so the user can re-read first.
- **Stats / Progress page (`StatsView`):** a sheet presented from a `chart.bar.fill` toolbar button in `ContentView`, left of the gear. Reads `FrequencyTracker.shared.snapshot()` once on `.task` into local `@State`, and reads `FamiliarityStore.shared` + `ActivityTracker.shared` directly (the `@Observable` macro tracks reads, so numbers update live when the user changes a familiarity level inside a nested modal). Four sections inside a `ScrollView` wrapped by a `NavigationStack` with `Color.paperBackground`:
  1. **Summary cards** — a 4-column `LazyVGrid` of `SummaryCard`s: *Unique words*, *Unique kanji*, *Known words* (vermillion-accented), *Known kanji* (vermillion-accented). Numbers use `.contentTransition(.numericText())` so they tick rather than snap when the user demotes a Known item from a nested modal.
  2. **Activity section** (`cardChrome`) — a 4-column `LazyVGrid` of `SummaryCard`s (*Day streak* vermillion-accented, *Sessions* = `totalStudySessions`, *Days studied*, *Today*) reading `ActivityTracker`, then **two** `ActivityChart`s (private view) under "Sentences · last 14 days" (`recentDays(14)`) and "Study sessions · last 14 days" (`recentStudySessions(14)`). Each chart draws bars growing upward from a shared baseline above narrow weekday labels, today's bar/label vermillion, empty days a faint accent stub; bar height scales to that chart's own max count. `ActivityChart` takes `days: [(date, count)]` so the same view renders both series.
  3. **Words section** (`cardChrome`) — a `DistributionBar` showing Unknown / Familiar / Known segments (gray-secondary / accent / vermillion) over a 14pt-tall `Capsule()`-clipped row, with a `LegendChip` row below, followed by the top 25 most-seen words. Each `WordRow` is a `Button` showing the word at 26pt serif + a familiarity `LevelDot` + the exposure count (`.callout.monospacedDigit`); tapping `openWord(_:)` asynchronously loads the cached definition from `DefinitionCache.shared`, constructs a minimal `Word(text:, reading: text, furigana: [single segment], definition:)`, and presents `WordDefinitionView` as a nested medium/large sheet. **Reading is intentionally not surfaced from stats** — `FrequencyTracker` only persists surface form, not pronunciation, so the modal's reading line (gated on `reading != text`) hides itself for kanji-containing words. The kanji within the word remain individually tappable via the existing per-character buttons in `wordHeader`.
  4. **Kanji section** (`cardChrome`) — same `DistributionBar` shape over kanji counts, then top 25 most-seen kanji at 36pt serif. Each `KanjiRow` tap presents `KanjiDetailView` directly (no async hop — `KanjiDetailView` already loads its own data).
  - **Export button** — a `square.and.arrow.up` toolbar item at `.topBarLeading` (disabled when both dicts are empty). Tapping runs `ExportService.makeExportFile()` (async — pulls the live `FrequencyTracker` snapshot + `FamiliarityStore`/`ActivityTracker`/`SavedSentenceStore` in-memory state), writes a pretty-printed, ISO8601-dated JSON document to the temp dir (`NihongoPro-Progress.json`), and presents it via `ShareSheet` (a `UIActivityViewController` `UIViewControllerRepresentable` in `ExportService.swift`) through `.sheet(item: $exportItem)`. The document bundles word/kanji frequencies, word/kanji familiarity, daily activity, daily study sessions, and saved sentences — a round-trippable mirror of every on-device store plus a small header (`exportedAt`, `appVersion`).
  - **Familiarity tallies** are reduce-based over `FamiliarityStore.shared.{word,kanji}Levels`, filtered by membership in `wordCounts`/`kanjiCounts` so a hypothetical orphan entry (none currently possible, but defensive) can't inflate the count. *Unknown* is computed as `total unique - familiar - known`, never stored.
  - **Top-N lists** are deterministic: sort by count desc, break ties by key asc, take 25. A footer `"+ N more"` line renders when the dict exceeds 25, signalling there's more data but intentionally not exposing it yet (the "show all" pathway is a future refinement).
  - **Empty state** — when both dicts are empty, the view shows a centred `chart.bar.xaxis` symbol + "No data yet" + a hint to parse a sentence first. The summary cards are not shown in this state.
  - **Concurrency** — `StatsView` is presented as a `.sheet(isPresented:)` from `ContentView` (a sibling sheet modifier, not chained inside settings). It in turn presents `WordDefinitionView`/`KanjiDetailView` as nested sheets via `.sheet(item:)`. iPadOS handles the stacking natively.
- **Persistent definition cache (`DefinitionCache`):** actor singleton (`DefinitionCache.shared`) that backs both `fetchKanjiInfo(kanji:)` and `fetchDefinitions(sentence:words:)`. Two JSON files in `applicationSupportDirectory/NihongoPro/`: `kanji_cache.json` (`[String: KanjiInfo]`) and `word_cache.json` (`[String: String]`). Files are loaded into memory in the actor's init and persisted on every set call (atomic write). Cache hits skip the Claude round-trip entirely.
  - **Kanji:** keyed by the kanji character. `fetchKanjiInfo` checks cache first; on miss, calls Claude and stores the result. `KanjiInfo` is `Codable`.
  - **Word definitions:** keyed by surface form (`Word.text`), stored in `word_definitions.json`. `fetchDefinitions` does **partial fetch**: for each input word it (a) marks it `nil` if `isPurePunctuation(_:)` (CharacterSet of `.punctuationCharacters` + `.whitespacesAndNewlines`), (b) pulls from cache if known, (c) collects the rest as `uncachedIndices`. If `uncachedIndices` is empty, no API call is made. Otherwise the sentence is sent with just the uncached words; returned definitions get spliced back into the original indices.
  - **Polysemy guard:** the definitions response includes a `context_dependent: [bool]` array aligned with `definitions`. Claude marks `true` for polysemous words whose meaning varies meaningfully across common contexts (走る, 開く, 持つ, 出る, 取る, 立つ, 上がる…) and `false` for words with one dominant sense (今日, 食べる, particles, copulas). Only definitions where `context_dependent == false` are written to the cache. If the flag is missing/malformed, the iOS side defaults to `true` (don't cache) — fail-safe. The polysemy guidance lives in `definitionsSystemPrompt`. On app upgrade to this version, the actor's `init` deletes the legacy `word_cache.json` (entries may include polysemous words from before the flag existed) and starts fresh in `word_definitions.json`.
- **Dictionary handoff buttons:** two small SwiftUI `Link` buttons live in `Theme.swift` and are stacked just below the familiarity picker in both `WordDefinitionView` and `KanjiDetailView`:
  - `NihongoLookupLink(kind:query:)` — opens `https://nihongo-app.com/dictionary/word/<query>` or `/kanji/<query>`. Universal-link form, per Chris Vasselli's (Nihongo's developer) explicit recommendation over the `nihongo://` URL scheme that Apple is deprecating. Routes to the installed Nihongo app and falls back to the web dictionary page in Safari otherwise.
  - `JishoLookupLink(kind:query:)` — opens `https://jisho.org/search/<query>` for words; for kanji it appends ` #kanji` to the query (becomes `<query>%20%23kanji` after encoding) so Jisho lands directly on the kanji detail page rather than the general search results. Web-only — there's no Jisho iOS app — so always opens in Safari.
  - Both views use `addingPercentEncoding(withAllowedCharacters: .urlPathAllowed)`, which correctly encodes Japanese characters, spaces (→ `%20`), and `#` (→ `%23`). Both render as `.bordered`/`.controlSize(.small)` with the `arrow.up.forward.app` SF Symbol. Both hide themselves if the query trims to empty.
- **Stroke renderer:** `KanjiStrokeView` is fully native SwiftUI (no WKWebView). `extractStrokes(from:)` finds the `kvg:StrokePaths` section in the SVG with a regex and extracts each `<path d="...">`. `SVGPathParser.parse(_:)` (adapted from the sibling **kanji-concept** project) converts each d-string into a SwiftUI `Path` plus the start point of the first subpath. `StrokeAnimator` (`@StateObject`, MainActor `ObservableObject`) sequences per-stroke `withAnimation(.linear)` trims with duration scaled by the stroke's bounding-box diagonal. `StrokeCanvas` renders a 109-unit square with a faint grid + dashed crosshair, completed strokes at `Color.primary.opacity(0.25)`, the active stroke at full `Color.primary`, and an 18pt accent-color numbered badge at each stroke's start point. Replay is implemented by `.id(animationKey)` on the view; bumping the key forces a fresh parse + `animator.play(strokes:)`.
- **Breakdown view:** a Breakdown button sits to the right of Translate. Tapping replaces the English translation with the Markdown breakdown rendered by `BreakdownView` (custom mini-renderer handling `#`/`##`/`###` headings, `-`/`*` bullets, paragraphs, and inline `**bold**` / `*italic*` via `AttributedString`) and **hides the Breakdown button itself** — the action is one-way for the current sentence. Tapping Translate (with the same or different input) resets `showingBreakdown` to false and brings the Breakdown button back. The Markdown is cached in `ContentView.breakdown` for the lifetime of the current translation.
- **Clear button:** a destructive-role `.bordered` Clear button sits on the bottom-left of the action row (a `Spacer()` separates it from Show translation/Breakdown on the right). `ContentView.clear()` cancels any pending `autoParseTask`, resets `inputText`, `words`, `englishTranslation`, `isTranslationRevealed`, `parsedInputText`, all error/breakdown/loading state, and calls `speechService.stop()` if audio is still playing. Disabled while a translation is in flight or when there is nothing to clear (empty input AND empty results AND no error).
- **Spoken Japanese (TTS):** `SpeechService` (NSObject `ObservableObject`, exposes `isSpeaking`) has **two playback paths**, chosen per-call inside `speak(_:)`:
  - **On-device (default / offline):** `AVSpeechSynthesizer` for ja-JP. Voice selection respects a user-chosen `AVSpeechSynthesisVoice.identifier` stored in `UserDefaults` under `speechVoiceIdentifier`; empty/unset falls back to the highest-quality installed ja-JP voice (premium > enhanced > default).
  - **Premium (optional, ElevenLabs):** when `usePremiumVoice` (UserDefaults bool, set by the Settings toggle) is on **and** an ElevenLabs key is present in the Keychain (`KeychainStore.read(account: .elevenLabs)`), `speak(_:)` routes through `ElevenLabsService.synthesize(_:voiceID:apiKey:normalize:)` (model `eleven_turbo_v2_5` with `language_code: "ja"`, `xi-api-key` header, returns MP3) and plays it via `AVAudioPlayer`. `Self.premiumActive` (the toggle **and** a non-empty Keychain key) is the single source of truth for "premium will actually run" — callers read it to decide whether to katakana-prepare the text (see the sokuon note below). `apply_language_text_normalization` is now **conditional** (`normalize:` param): on for input containing kanji, off for pure-kana input (`text.contains { $0.isKanji }` in `speakWithElevenLabs`) — the normalizer has nothing to resolve on pure kana and can itself re-mangle the sokuon. **The model + params matter:** Turbo v2.5 honors `language_code` (so kanji reads as Japanese) and renders the chosen Voice Library voice on the standard endpoint. `eleven_multilingual_v2` ignores `language_code` and mis-reads bare kanji (e.g. 精米歩合) as Chinese — never use it. `eleven_v3` was tried and **failed on the `/v1/text-to-speech` endpoint** — the request errored and the app silently fell back to the Apple voice (robotic, ignores the chosen premium voice), which is exactly how a premium-path failure presents. `apply_language_text_normalization` (when on) runs ElevenLabs' Japanese normalizer over the text so we can feed **natural kanji** (which gives natural prosody) and still get correct kanji readings — feeding pre-flattened kana instead made the voice read flat/robotic. It adds latency, but output is cached so it's a one-time cost per sentence. `isSpeaking` is set optimistically at fetch start so the stop control shows during the network round-trip; `stop()` cancels the in-flight `fetchTask` and stops both the synthesizer and the player. **Any** failure (offline, bad key, quota, decode) falls back to the on-device voice via `fallBackToApple(_:)` — the app always speaks something. Fetched MP3s are cached to `cachesDirectory/ElevenLabsAudio/<sha256(model|voiceID|norm<bool>|text)>.mp3` (SHA256 via CryptoKit; the `norm<bool>` component means flipping normalization re-fetches rather than serving stale audio), so replays and previously-heard saved sentences play offline. The voice ID used for synthesis is UserDefaults `elevenVoiceID` (empty → `ElevenLabsService.defaultVoiceID`, the "Rachel" premade voice — an English voice, so the user is expected to pick a Japanese one).
  - **Voice selection (Voice Library):** the default `/v1/voices` list only returns the account's *premade English* voices — useless for Japanese. So the Settings picker instead lists **native Japanese voices from the public Voice Library** via `ElevenLabsService.fetchJapaneseVoices(apiKey:)` (`GET /v1/shared-voices?language=ja&page_size=100` → `SharedVoice` items with `voice_id`, `public_owner_id`, `name`, `accent`, `use_case`, `preview_url`). Each row has a **free sample button** that plays the voice's `preview_url` via `SpeechService.playPreview(_:)` (downloads the MP3 and plays through the same `AVAudioPlayer` path — **no** synthesis cost). Selecting a row calls `selectVoice(_:)`, which **adds** the library voice to the account (`ElevenLabsService.addSharedVoice(publicOwnerID:voiceID:name:apiKey:)` → `POST /v1/voices/add/{owner}/{voice}` body `{new_name}` → owned `voice_id`) and stores that owned id in `elevenVoiceID` plus the display name in `elevenVoiceName`. Library voices can't be synthesized directly — they must be added first (consuming an ElevenLabs voice slot), so `selectVoice` first checks the account's existing voices (`fetchVoices`) and reuses a same-named one rather than re-adding. Auditioning via sample is free; only an explicit selection consumes a slot.
  - **Sentence vs single-word speech input:** the two contexts feed different text on purpose. The core problem: feeding the engine raw **kanji** sounds natural but mis-reads rare compounds (精米歩合 → "seimebukara"); feeding pure **kana** reads correctly but flat/robotic. Neither global setting nor ElevenLabs' `apply_language_text_normalization` fixes ultra-rare readings. The solution is **selective kana substitution**, using the `tts_kana` flag from pass 1.
    - **Full sentence** (`ContentView.translate()` auto-play and the replay speaker button both speak `words.sentenceSpeechText(katakana:)` — the `[Word]` extension in `TranslationService.swift`): each word is spoken as its **kanji surface form** unless `ttsKana == true`, in which case it's swapped to its **kana reading**. So a sentence stays mostly natural kanji (good prosody) with only the tricky words (e.g. 精米歩合 → せいまいぶあい) converted.
    - **Arabic digits are deliberately left as-is (do NOT re-add digit→kana conversion).** This was tried and reverted. The chain: feeding raw digits into ElevenLabs' `apply_language_text_normalization` makes its LLM normalizer mis-read them ("6"→English "six") and even *leak its own reasoning into the audio* ("…let me redo this with numbers converted to hiragana…"). The obvious fix — convert digits to their reading before sending — works for correctness but **wrecks prosody**: any kana (or kanji-numeral) island injected into the kanji text gets phrased by ElevenLabs as its own chunk, inserting pauses in the wrong places and making the whole sentence sound stilted. Kanji numerals (6県 → 六県) additionally mis-read (六 is ambiguous → むつ). Terry chose **natural prosody over number correctness** for the premium voice: numbers in number-heavy (often news) sentences may occasionally read wrong/English, but the sentence flows naturally. The conversion code (`arabicDigitsToKana`, `containsDigit`, the kana number-reading tables) was removed in full. If this resurfaces, the lever is *not* text munging — it's whether a future ElevenLabs model/param normalizes Japanese numbers without the English/meta-leak bug.
    - **Single word** (`WordDefinitionView` per-word button speaks `[word].sentenceSpeechText(katakana:)` — i.e. the *same* selection rule as a one-word sentence): the **kanji surface form** unless `ttsKana == true`, in which case the kana reading. This was changed from always-kana after a by-ear finding: ElevenLabs reads the **kanji** correctly but **truncates a terminal っ/つ when fed bare kana of either script** (温帯低気圧 → "…おんたいていきあ", the final つ swallowed as a glottal stop). The sentence path already feeds non-flagged words as kanji, so the same word spoken *in a sentence* was correct while the single-word button (old always-kana path) was wrong — that asymmetry is what isolated the cause. The rare-compound case (精米歩合) is still covered because those words are `ttsKana`-flagged and so still drop to kana. (`StatsView` builds a minimal `Word` with `reading == text` and `ttsKana == nil`, so its word playback feeds the surface form — unchanged.)
    - **Katakana prep + normalization-off on the premium path (sokuon levers, scoped to flagged words):** both speech call sites pass `katakana: SpeechService.premiumActive`. When premium is actually active, the **substituted kana** (only the `ttsKana`-flagged words — the natural kanji words stay kanji) are converted hiragana→katakana via `Word.toKatakana(_:)` (U+3041–U+3096 → +0x60; っ U+3063 → ッ U+30C3), and `apply_language_text_normalization` is turned off for the resulting pure-kana input. **Important:** the decisive root cause turned out to be **kanji-vs-kana, not hiragana-vs-katakana** — feeding kanji is what fixes the sokuon, so the primary fix is "prefer kanji" (the single-word change above). The katakana swap + normalization-off now only affect the rare `ttsKana`-flagged words, where we have *no choice* but to feed kana (the kanji mis-reads); they're a best-guess belt-and-suspenders for that narrow case and remain **unverified by ear** for flagged words. **Phoneme/IPA tags are not an option** — ElevenLabs phoneme tags are English-only and silently skipped for Japanese. The Apple path keeps hiragana. If a *flagged* rare word still mis-geminates, the next lever is a per-word pronunciation-dictionary alias.
  - Playback fires automatically **after** the Claude response lands (so the audio is synchronized with the visual reveal of the furigana + translation) and on demand via a speaker/stop button in the Japanese display area. Failed requests do not play audio. **Rate** (Natural / 85% / 65%, key `speechRate`) applies to both paths: as the `AVSpeechUtterance.rate` multiplier on the Apple path and as `AVAudioPlayer.rate` (`enableRate = true`) on the premium path. The Settings sheet lists every installed ja-JP voice (Apple) plus a separate "Premium Voice (ElevenLabs)" section (toggle + key field + Japanese Voice Library list with per-voice samples), with a shared Play Sample button that exercises whichever path is active.
- **API key storage:** iOS Keychain (`kSecClassGenericPassword`, service `com.terrydonaghe.NihongoPro`). `KeychainStore` is keyed by a `KeychainStore.Account` enum — `.anthropic` (`anthropic-api-key`, the default for all `read/save/delete`) and `.elevenLabs` (`elevenlabs-api-key`, for the optional premium voice). Both entered in-app via `SettingsView` (Anthropic on first launch, ElevenLabs in the Premium Voice section); re-openable via gear icon. No xcconfig/Secrets file.
- **Dependencies:** none third-party (no SPM, no CocoaPods). System frameworks only: Foundation, SwiftUI, Security (Keychain), AVFoundation (TTS + `AVAudioPlayer`), CryptoKit (audio-cache hashing). Network data: KanjiVG (CC BY-SA 3.0, fetched on demand) and — only when the user opts in with their own key — the ElevenLabs TTS API.
- **Trigger:** debounced auto-parse on `inputText` change (800ms). Translation reveal is gated behind the **Show translation** button so the user can attempt to read the sentence first.
- **Device target:** iPad only (`TARGETED_DEVICE_FAMILY = 2`), iPadOS 26+ (`IPHONEOS_DEPLOYMENT_TARGET = 26.0`).
- **Bundle ID:** `com.terrydonaghe.NihongoPro`.

## Build & run

Open `NihongoPro.xcodeproj` in Xcode and Run on an iPad simulator. Headless build for verification:

```bash
xcodebuild -project NihongoPro.xcodeproj -scheme NihongoPro \
  -destination 'generic/platform=iOS Simulator' \
  -configuration Debug build CODE_SIGNING_ALLOWED=NO
```

Always run this after editing Swift files or pbxproj — SourceKit diagnostics shown during edits are noisy and unreliable; the actual build is the source of truth.

## Adding a new Swift source file

The pbxproj uses readable sequential IDs of the form `FA00000000000000000000{XY}`. When adding `NewFile.swift`:

1. Pick the next unused suffix (e.g. `A9` for the file ref, `B9` for the build file).
2. Add a `PBXFileReference` line in the PBXFileReference section.
3. Add a `PBXBuildFile` line in the PBXBuildFile section.
4. Add the file ref `A9` to the `FA00000000000000000000D1 /* NihongoPro */` group's `children`.
5. Add the build file `B9` to the `FA00000000000000000000E1 /* Sources */` build phase's `files`.
6. Rebuild with the xcodebuild command above.

## Tuning behavior

- **Translation/furigana quality:** edit `translationSystemPrompt` in `TranslationService.swift` (pass 1). This prompt also owns the `tts_kana` per-word flag that drives selective kana substitution for speech — if rare words are mispronounced (flag missed) or speech sounds flat (over-flagging), tune the `tts_kana` guidance/example there. Definition quality lives in `definitionsSystemPrompt` (pass 2). Breakdown depth and structure live in `breakdownSystemPrompt`. Per-kanji info shape lives in `kanjiInfoSystemPrompt`. Keep the worked example in each prompt — they reliably anchor Claude's output shape (JSON for passes 1/2/kanji, Markdown for breakdown).
- **Stroke order animation:** `KanjiStrokeView` is fully native SwiftUI (see Tap-to-explore-kanji above for the render pipeline). To tune the look: stroke thickness, completed-stroke opacity, badge size, and grid/dash colors all live in `StrokeCanvas` inside `KanjiStrokeView.swift`. Per-stroke duration scaling lives in `StrokeAnimator.duration(for:)`. Replay is implemented by bumping `KanjiDetailView.animationKey` which `.id()`-keys the `KanjiStrokeView` — SwiftUI discards and recreates the view, which re-parses the SVG (cheap, ~ms) and starts a fresh `animator.play(strokes:)`. Cache directory for fetched SVGs is `FileManager.default.urls(for: .cachesDirectory, ...)` so files may be evicted under disk pressure; refetch is automatic.
- **Furigana display:** `FuriganaText` view exposes `showFurigana`, `drillMode`, `baseFont`, `rubyFont`, `rubyColor`, `wordSpacing`, `lineSpacing`, and `onWordTap` parameters. Outside drill mode, each word is wrapped in a `Button` and disabled when `definition == nil` (punctuation). Tappable words get a 1.5pt `.tint`-colored underline via a bottom overlay inside `WordView` (now driven by the explicit `underline:` parameter); punctuation gets no underline. In drill mode (`drillMode == true`) the tap toggles per-word reading reveal instead — see the **Reading drill mode** architecture note. The flow-wrap logic is `FuriganaFlowLayout` in the same file. Note: wrapping words in `Button` removes per-character text selection on the Japanese display in exchange for tap-to-define; the English translation below remains selectable.
- **Definition sheet:** `WordDefinitionView` is a small SwiftUI view shown via `.sheet(item:)` with `.presentationDetents([.medium, .large])`. The selection state lives in `ContentView.selectedWord: WordSelection?` (a UUID-id wrapper around `Word` so `.sheet(item:)` works even when the same word appears twice). The sheet receives the shared `SpeechService` via init (`@ObservedObject`) so its play/stop button reflects the same `isSpeaking` state as the main display — closing the sheet while audio is still playing does not stop it.
- **TTS tuning:** voice selection priority is in `SpeechService.selectedVoice()` (UserDefaults override → `bestJapaneseVoice()` fallback). Quality-tier fallback is in `bestJapaneseVoice()` / `availableJapaneseVoices()` — change the sort order to change auto-pick behavior. Rate multipliers are in `SpeechRate.multiplier`. Audio session uses `.ambient` (set on the premium path before `AVAudioPlayer.play()`) so the device silent switch silences playback; to force playback regardless, use `.playback`. `SettingsView` reads `SpeechService.availableJapaneseVoices()` to populate its Voice picker — `SettingsView` takes the live `SpeechService` instance via init so the Play Sample button shares state with the main display.
- **Premium voice (ElevenLabs) tuning:** the model is `ElevenLabsService.modelID` (`eleven_turbo_v2_5`) and the forced language is `ElevenLabsService.languageCode` (`ja`, sent as `language_code`). **Do not switch to `eleven_multilingual_v2`** (ignores `language_code` → kanji read as Chinese) **or `eleven_v3`** (errors on the `/v1/text-to-speech` endpoint → silent Apple fallback that presents as a robotic voice ignoring the premium pick). `apply_language_text_normalization` (the Japanese normalizer that lets us feed natural kanji — now passed as the `normalize:` param, on for kanji input / off for pure kana, decided in `SpeechService.speakWithElevenLabs`) and `voice_settings` (stability/similarity_boost) and the request shape live in `ElevenLabsService.synthesize`. Note the silent-fallback behavior: any premium synthesis error drops to the Apple voice (`fallBackToApple`), so "robotic voice that ignores the selected premium voice" is the signature of a failing ElevenLabs request, not a bad voice. The fallback voice when the user hasn't picked one is `ElevenLabsService.defaultVoiceID`. The audio cache key/dir is in `SpeechService.cacheURL(text:voiceID:normalize:)` (key `model|voiceID|norm<bool>|text`) — bump it (or change `modelID`) to invalidate cached MP3s. The premium↔Apple routing decision is the `Self.premiumEnabled` + Keychain check at the top of `SpeechService.speak(_:)` (also exposed as `Self.premiumActive` for callers that katakana-prepare text); the fallback-on-error path is `fallBackToApple(_:)`. **Sokuon (っ/つ) fix:** if the small/large tsu still swap on the premium voice, the levers are the katakana prep in `Word.spokenText(katakana:)`/`sentenceSpeechText(katakana:)` and the normalization toggle — phoneme tags are English-only on ElevenLabs and can't be used for Japanese. **Voice picker:** the Settings list is sourced from the Voice Library, filtered to Japanese, in `ElevenLabsService.fetchJapaneseVoices` (`?language=ja`) — change the query items there to widen/narrow the list (e.g. `accent`, `gender`, `search`, `category`). Per-voice samples play `SharedVoice.preview_url` for free via `SpeechService.playPreview`; selection/add-to-account logic is `SettingsView.selectVoice`. If the Japanese list comes back empty, the `language=ja` filter value is the thing to revisit.
- **Input validation:** `ContentView.isMultiSentence(_:)` uses `String.enumerateSubstrings(in:options: .bySentences)` (ICU's sentence breaker — handles 。!?！？ and quoted text reasonably) to count sentences; >1 disables the Translate button and shows an inline orange warning below the text editor. Long single sentences are intentionally allowed — there is no character limit, only a sentence-count limit.
- **Model:** `TranslationService.model` constant. Sonnet 4.6 is the chosen balance; Haiku is cheaper but weaker on idiomatic readings, Opus is overkill for sentence-level.
