# Nihongo Pro — context for Claude

Personal Japanese-study app for iPad and iPhone. SwiftUI, universal (iPadOS / iOS 26+), single target, zero third-party dependencies. Primarily designed for iPad; the iPhone layout is an adaptation gated on device idiom so the iPad UI is byte-identical to before iPhone support was added (see **iPhone adaptation** below).

## Visual identity

- **Palette** (defined in `NihongoPro/Assets.xcassets/`):
  - `AccentColor` — deep indigo (kon-iro), light `#2A3A6B`, dark `#7BA0E0`. Used everywhere SwiftUI reads `.tint` / `.accentColor`.
  - `PaperBackground` — warm cream / off-black. Light `#FFFCF5`, dark `#1A1814`. Applied as `Color.paperBackground.ignoresSafeArea()` behind the main screen and the two modals. Auto-generated by Xcode's asset symbol generation (`ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS = YES`), so the property name is `paperBackground` (camelCased from the asset name), not the asset filename.
  - `Vermillion` — warm red-orange (shu-iro), light `#DC4F35`, dark `#F1715A`. Reserved as a celebratory accent — currently used for "Known" indicators in `StatsView` (summary cards + `LevelDot` + the Known segment of the `DistributionBar`). Not used for primary buttons (those stay indigo accent).
  - `KnownGreen` / `LearningYellow` — knowledge-markup colors for the sentence display (see **Knowledge markup** below). `KnownGreen` light `#2E7D4C`, dark `#7CC98F`; `LearningYellow` is an amber (pure yellow is illegible on the cream paper), light `#B07D10`, dark `#E3B341`. Mapped from `FamiliarityStore.Level` by the `markupColor` extension in `Theme.swift` (`known` → green, `familiar` → amber, `unknown` → `nil` = default/tint).
  - `.orange` / `.red` keep their semantic roles (warning / destructive). Orange also drives the pomodoro break overlay scrim and the "on break" tint of `PomodoroPill`.
- **Card chrome** — `cardChrome(cornerRadius:padding:)` View extension in `NihongoPro/Theme.swift`. Applies `.padding`, `.regularMaterial` rounded background, and a soft shadow (`black.opacity(0.06)`, radius 12, y 2). Used on: the parsed-sentence card on the main screen, the top word-header card in `WordDefinitionView`, the info card in `KanjiDetailView`, and the Words / Kanji sections in `StatsView`.
- **Typography tokens** in `Theme.swift`: `Font.displayKanji` (96pt serif), the hero glyph size in `KanjiDetailView`. (The former `displayWord`/`sentenceLarge` tokens were never referenced and have been removed — the other large display sizes are inline `Font.system(size:design:.serif)` calls at their point of use.)
- **Motion** — Break overlay scale-fades in via spring. `PomodoroPill`'s seconds use `.contentTransition(.numericText())` so digits tick rather than snap; icon swaps use `.symbolEffect(.replace)`. The `TextEditor` on the main screen animates its border tint when focus changes (`.smooth(duration: 0.2)`). Main-screen state changes are animated: `translationDisplay` crossfades between loading/empty and scale-fades the parsed card in (transitions keyed on `words.isEmpty` / `isTranslating`); the translation reveal and the breakdown ⇄ translation swap slide-fade in from the bottom (`.opacity + .move(edge: .bottom)`, keyed on `isTranslationRevealed` / `showingBreakdown` in `parsedSentenceCard`). Both speaker buttons (sentence card + `WordDefinitionView`) use `.symbolEffect(.pulse, isActive: isSpeaking)` on the stop icon plus a `.replace` content transition on the play⇄stop swap. Drill-mode reading reveals fade via `withAnimation(.smooth(duration: 0.2))`. Sentence words use `WordTapStyle` (private `ButtonStyle` in `FuriganaText.swift`: 0.96 scale + dim while pressed) instead of `.plain` so tap-to-define has touch feedback. In `StatsView`, `ActivityChart` bars grow up from the baseline with a slight left-to-right stagger on appear, and `DistributionBar` sweeps in from the left on appear and animates live count changes.
- **Empty state (main screen)** — a faint serif 読 watermark (`Color.accentColor.opacity(0.22)`, 96pt) above the paste prompt, echoing the app icon; replaced the earlier generic `text.book.closed` symbol.

## Architecture (locked-in decisions)

- **iPhone adaptation (universal layout):** the app is universal (`TARGETED_DEVICE_FAMILY = "1,2"`). iPhone is **portrait-only** (`UISupportedInterfaceOrientations` = Portrait in `Info.plist`); iPad keeps all four orientations via the separate `UISupportedInterfaceOrientations~ipad` key. Every iPhone-specific layout branch is gated on **device idiom** — `private var isPhone: Bool { UIDevice.current.userInterfaceIdiom == .phone }` (computed locally in `ContentView` and `StatsView`) — deliberately **not** `horizontalSizeClass`, so the iPad layout is byte-identical to before (an iPad in a narrow Slide Over reports a compact size class and would otherwise wrongly get the phone layout; portrait-locking the phone also removes any landscape size-class edge case). Each branch is `isPhone ? <new> : <existing>`, so the iPad path is untouched. iPhone differences vs iPad:
  - **Outer padding** in `ContentView.body` is `16` on iPhone vs `32` on iPad.
  - **Toolbar:** the Drill and Furigana toggles stay as individual `topBarTrailing` items in both. On iPhone, Library / Stats / Settings collapse into a **single `Menu`** (`ellipsis.circle`, `Label`-based items) instead of three separate toolbar buttons; on iPad they remain three buttons. The study-session pill + end-session button are unchanged in both.
  - **Action button row** (`inputArea` bottom): on iPad it's the existing `HStack` with `Spacer()` and fixed `minWidth`s; on iPhone it's a `VStack` of **full-width** buttons (primary action on top: Show translation → Breakdown → Start study, then Clear at the bottom). Both paths render the **same** four extracted `@ViewBuilder` button properties (`clearButton` / `showTranslationButton` / `breakdownButton` / `startStudyButton`) so conditions and disabled-state never drift; the only difference is the container and the `ActionButtonWidth` modifier (file-scope `ViewModifier`) which applies `maxWidth: .infinity` on iPhone vs `minWidth:` on iPad.
  - **StatsView grids:** the two `SummaryCard` `LazyVGrid`s (summary cards + Activity cards) use a shared `summaryColumns` computed property — **2 columns** on iPhone, **4** on iPad.
  - **Audio session:** iPhone uses `.playback` so the ring/silent switch can't mute study audio; iPad keeps `.ambient`. Same `isPhone` idiom gate, implemented in `SpeechService` (see TTS tuning below).
  - **Keyboard dismissal:** the `TextEditor` adds a `.keyboard`-placement `ToolbarItemGroup` (a `Spacer` + a "Done" / `keyboard.chevron.compact.down` button that sets `isInputFocused = false`) **only on iPhone**, and the sentence `ScrollView` uses `.scrollDismissesKeyboard(isPhone ? .interactively : .automatic)` so dragging the sentence area also dismisses it. The software keyboard otherwise eats too much of the small screen; iPad (which has no such constraint) gets neither change. Everything else (sheet detents, KanjiStrokeView's `GeometryReader`, FuriganaFlowLayout, the 96pt/64pt display fonts, SettingsView `Form`, LibraryView `List`) already adapts to the ~440pt-wide phone with no change.
- **AI provider switch (Claude ⇄ ChatGPT):** the AI calls go through one provider, chosen by a segmented picker at the top of `SettingsView` and stored in `@AppStorage("aiProvider")` (`AIProvider` enum — `.anthropic` / `.openai`, default `.anthropic` — declared at the top of `TranslationService.swift`). `TranslationService.sendMessage(systemPrompt:userMessage:maxTokens:)` reads `TranslationService.provider` (a static computed that reads UserDefaults live, so a Settings change takes effect on the next call) and dispatches to `sendAnthropicMessage` (Anthropic Messages API, `claude-sonnet-4-6`, `x-api-key` header, `system` + `messages`, text at `content[].text`) or `sendOpenAIMessage` (OpenAI Chat Completions, `gpt-4.1`, `Authorization: Bearer` header, system+user `messages`, text at `choices[0].message.content`). Both take the **same** system/user prompts and return the model's text, so the four public methods, JSON extraction, parsing, caching, and retry logic are entirely provider-agnostic — the only fork is the one private send method. `gpt-4.1` is deliberately the classic Chat-Completions shape (`max_tokens`, no hidden reasoning tokens), which is why it slots in with no param changes; switching the OpenAI default to a GPT-5/o-series reasoning model would require `max_completion_tokens` and dropping custom temperature. OpenAI's error envelope is `{error:{message}}` — the same shape as Anthropic's — so the existing `APIErrorEnvelope` decodes both. The OpenAI model is the `TranslationService.openAIModel` constant (mirrors `model` for Claude). Keys are separate Keychain accounts (`.anthropic` / `.openai`) — see **API key storage** below. **Not** per-call-type: the whole app uses one provider at a time — with **one deliberate exception**: `fetchKanjiInfo`/`regenerateKanjiInfo` bypass the switch entirely and always call Anthropic via the dedicated `sendKanjiInfoMessage` (Opus 5, high-effort thinking — see **Tap-to-explore-kanji**), so kanji info needs the Anthropic key even when the provider is OpenAI.
- **AI activity indicator (`AIActivity`):** a `@MainActor @Observable` singleton (declared at the top of `TranslationService.swift`) counting in-flight AI requests, incremented/decremented at the two send choke points — `sendMessage` (translate/definitions/breakdown, both providers) and `sendKanjiInfoMessage` (all kanji info, background prefetch included) — via `begin()`/`end()` (the `end()` in a `defer { Task { @MainActor … } }` so errors also decrement). UI: the **leftmost `topBarTrailing` toolbar item** in `ContentView` — a `sparkles` image, accent-tinted, `.symbolEffect(.pulse, isActive:)` while requests are in flight. The item is **always present and opacity-gated** (0 ⇄ 1 with `.smooth(0.3)`) rather than conditionally inserted, so the icon cluster never shifts as requests start/finish; `accessibilityHidden` when idle.
- **Multi-pass translation:** pasting/typing into the input area kicks off two sequential Messages calls (through the provider-dispatching `sendMessage`, plain `URLSession`) after a debounce. A third on-demand call powers the Breakdown view.
  - **Auto-parse on input change:** `ContentView.handleInputChange()` (wired via `.onChange(of: inputText)`) cancels any in-flight `autoParseTask`, resets parsed state if the text differs from `parsedInputText`, and — when the input is non-empty, within the 200-char limit, and an API key is present — schedules a debounced `Task` that sleeps 800ms then calls `translate()`. The English translation is fetched in the same call but stays hidden until the user reveals it (see below). `translate()` captures the trimmed input at start and bails (without setting state) if `inputText` has changed by the time the network result returns, so racing pastes can't corrupt the display.
  - **Translation reveal:** `isTranslationRevealed` gates whether the translation is shown. The reveal renders an **uncaptioned** plain block via `ContentView.translationBlock` — `englishTranslation` in title2 secondary style, no LITERAL/NATURAL captions (the earlier two-block captioned display and its `labeledTranslation(_:_:)` helper were removed at Terry's request). Below it, a small `.bordered`/`.small` **"Show literal translation"** button appears (only when `literalTranslation` is non-empty); tapping it flips `isLiteralRevealed` (with a `.smooth(0.3)` animation) and swaps the button for the literal rendering in title3 **tertiary** style — visually subordinate to the natural translation, still uncaptioned. One-way for the current sentence, like the main reveal. `isLiteralRevealed` is reset to `false` at the same three sites as `isTranslationRevealed` (`clear()`, `load(_:)`, and the `handleInputChange()` new-input reset). The "Show translation" button only renders once `words` and `englishTranslation` are populated (i.e., the auto-parse has completed) — there is no impatient-user pathway; the user always sees the Japanese first, then the button appears. Tapping it simply flips `isTranslationRevealed = true`. The Breakdown button only appears post-reveal. `parsedInputText` tracks which input the current `words` / translations belong to so reveals never show a stale translation. `translationBlock` is shared by the reveal and the Breakdown header so the translation (and the literal button/text) appears identically in both.
  - **Literal translation (opt-in reveal):** a more literal, grammar-following English rendering (readable English preserving Japanese word/phrase order — topic first, verb/copula last). It rides along in **Pass 1** (a third `literal_translation` JSON field — no extra API call), decoded into `TranslationResult.literalTranslation` (defaults to "" if absent — defensive) and baked into `SavedSentence.literalTranslation` (optional, so old saved files decode). Displayed only on demand via the "Show literal translation" button inside `translationBlock` (see Translation reveal above); sentences without a literal (pre-feature saved sentences) simply never show the button. Tune its style in `translationSystemPrompt` (the `literal_translation` field guidance + worked example).
  - **Pass 1 — `TranslationService.translate(_:)`:** returns `{words: [{text, reading, furigana, tts_kana}], translation, literal_translation}`. No definitions. `tts_kana` is a per-word boolean (decoded into optional `Word.ttsKana`, absent ⇒ `false`) that Claude sets `true` only for words whose kanji reading is uncommon/non-obvious enough that a TTS engine would mis-read it (rare/technical compounds like 精米歩合, unusual name readings, ateji/gikun). It drives selective kana substitution for sentence speech — see the speech-input note below. Words/furigana are displayed as soon as it lands (and the sentence is spoken too, if the auto-read toggle is on — see TTS below); the translation is held back behind the reveal gate. On `.invalidResponseFormat`, `translate(_:)` retries once with the input passed through `sanitizeForJSON(_:)` — which **strips** all quote-like characters entirely (ASCII `"`/`'`, U+201C/D smart double, U+2018/19 smart single, U+201E/A/F low quotes, U+2032/33 primes, U+00AB/BB guillemets, U+301D-F double-prime quotation) and replaces ASCII `\` with `／` (U+FF0F). The original failing input was a sake brewery description containing mixed quote variants; even after replacing them with typographic quotes Claude still produced invalid JSON, so the retry path now drops quote chars entirely as the most reliable recovery. Fidelity tradeoff: quote characters disappear from the output on the retry path, but the sentence parses. `max_tokens` is 16384 here to leave headroom for multi-sentence passages (the 200-char input cap can mean 100+ word entries). JSON extraction (`Self.extractJSON`) is permissive: it strips code fences AND slices from the first `{` to the last `}` so any stray prose around the JSON doesn't break the decode. Parse-failure errors surface (a) detailed `DecodingError` info — `dataCorrupted` unwraps the underlying `NSError`'s `NSDebugDescription`; `keyNotFound`/`typeMismatch`/`valueNotFound` include the coding path — and (b) a generous `previewSnippet` of the raw response (600 head + 600 tail with middle elided), so future failures are diagnosable from the in-app error banner alone.
  - **Pass 2 — `TranslationService.fetchDefinitions(sentence:words:)`:** takes the `[Word]` (not bare strings) and sends `{sentence, words: [{text, reading}]}` — the pass-1 `reading` rides along so the model romanizes/disambiguates from the **authoritative** reading instead of re-guessing the kanji (the prompt says the provided reading overrides any inferred reading, which fixes e.g. the name 安青錦 → "Aonishiki" rather than "Yasuaonishiki"). Gets back `{definitions: [String?]}` aligned to the words by index. Cache lookups/writes still key on the surface `text`. `ContentView` merges the array into the existing `words` state (`Word.definition` is `var`). A subtle "Loading word definitions…" indicator appears below the English translation while pass 2 runs; on failure it becomes a "Couldn't load definitions" message with a Retry button.
  - **On-demand — `TranslationService.fetchBreakdown(sentence:words:translation:)`:** fired only when the user taps the Breakdown button. Sends the sentence, the per-word data (including any definitions from pass 2), and the English translation; gets back Markdown with these sections in order: `## Vocabulary`, `## Grammar`, `## Sentence structure`, `## Notes` (the prose commentary). `ContentView.breakdownContent` renders the shared `translationBlock` (the natural translation) **above** the `BreakdownView` so the reader sees the meaning, then the structural breakdown, then the Notes paragraph at the bottom. The Markdown is cached in `ContentView.breakdown` for the current translation and survives toggling.
  - Four system prompts pinned in `TranslationService.swift` (`translationSystemPrompt`, `definitionsSystemPrompt`, `kanjiInfoSystemPrompt`, `breakdownSystemPrompt`) — each includes a worked example to lock in output shape. Translation, definitions, and breakdown go through the shared private `sendMessage(systemPrompt:userMessage:maxTokens:)` helper, which dispatches to the Claude or ChatGPT path per the **AI provider switch** above (the prompts are identical for both providers). Kanji info is the exception — it uses the dedicated Anthropic-only `sendKanjiInfoMessage` (see **Tap-to-explore-kanji**).
- **Tap-to-define:** every word in the Japanese display is a `Button` in `FuriganaText`, disabled while `definition == nil`. The 3pt accent underline that marks a word as tappable is also gated on `definition != nil`, so it only appears after pass 2 lands. Tapping a tappable word opens `WordDefinitionView` as a medium-detent sheet showing the word, kana reading, English definition, and a speaker/stop button that plays just that word using the shared `SpeechService`.
- **Tap-to-explore-kanji:** inside `WordDefinitionView`, the large word header is rendered character-by-character. Kanji characters (CJK Unified Ideographs — `Character.isKanji`) become tinted, underlined `Button`s; hiragana/katakana/punctuation render as plain `Text`. Each kanji button's tint follows its familiarity level via `WordDefinitionView.kanjiTint(for:store:)` — the same `markupColor` mapping as the sentence view's knowledge markup (Known → `KnownGreen`, Familiar → `LearningYellow`), falling back to `.tint` for unrated kanji so the indigo "tappable" cue is unchanged. `wordHeader` reads `FamiliarityStore.shared` in `body`, so `@Observable` tracking re-colors the header live when a rating changes in the nested `KanjiDetailView`. Tapping a kanji presents `KanjiDetailView` as a nested medium-detent sheet showing the character, English meanings, on'yomi/kun'yomi readings, the JLPT level (a "JLPT" labeled row, e.g. "N4" — hidden when the kanji is on no JLPT list; the level is AI-supplied per the widely-used unofficial post-2010 community lists via the `jlpt: Int?` field on `KanjiInfo`, so it's approximate for borderline kanji), an example word (an "Example" labeled row: serif word + reading · meaning), the kanji's visible **components** (tertiary caption line, e.g. "穴 hole · 心 heart"), a **component-based mnemonic** (a cause-and-effect story built only from those parts, landing on the primary meaning — replaced the old free-form "memorable note"; `note` stays on `KanjiInfo` only so pre-mnemonic entries decode, and the view falls back to showing it when `mnemonic` is nil), and a natively-rendered animated stroke order via `KanjiStrokeView`. The study aids (`components`/`mnemonic`/`example` on `KanjiInfo`, all optional) are the **same fields and prompt guidance as the kanji-study sibling app** — including the bad-vs-good 展 example that anchors mnemonic quality. All info comes from `TranslationService.fetchKanjiInfoBatch(_:extraInstruction:)` — a **batch** call (up to 8 kanji per request, input JSON array, output `{"kanji":[KanjiInfo…]}`; the prompt is now the **same batch prompt as kanji-study's** `KanjiInfoService.systemPrompt`), with `fetchKanjiInfo(kanji:)`/`regenerateKanjiInfo(kanji:)` as batch-of-1 wrappers. Unlike every other AI call it **bypasses the provider switch** and always calls Anthropic via the private `sendKanjiInfoMessage`: model `TranslationService.kanjiInfoModel` (`claude-opus-5`), high-effort thinking (`output_config.effort: "high"` — Terry explicitly chose mnemonic quality over latency, matching kanji-study; don't lower it), `fallbacks: "default"` with the `server-side-fallback-2026-07-01` beta header, and a 300 s `kanjiInfoTimeout` (Opus with thinking can exceed the 60 s URLRequest default). **Background prefetch (`KanjiInfoPrefetcher`):** a `@MainActor` singleton (declared at the bottom of `TranslationService.swift` — no new pbxproj entry) that fills the cache while the app is in use so the kanji sheet opens instantly. Two feeds into one deduped queue drained by a serial worker in batches of `batchSize` (8): `ContentView.translate()` enqueues the just-parsed sentence's kanji at the **front** (`priority: true`), and `NihongoProApp` calls `enqueueBacklog()` once per launch **after** `SyncCoordinator.start()` (every seen kanji from `FrequencyTracker`, most-seen first — after sync so entries fetched elsewhere aren't re-bought). Cache membership is checked at fetch time, not enqueue time, so CloudKit adoptions and earlier batches are skipped for free; failures are logged and skipped (`missingAPIKey` clears the queue); no-ops entirely without an Anthropic key. `KanjiDetailView.loadInfo` goes through `KanjiInfoPrefetcher.ensure(_:)` — cached → instant, in-flight → waits (250 ms poll), otherwise fetches immediately, jumping the queue. A **"New mnemonic"** borderless caption button under the mnemonic calls `TranslationService.regenerateKanjiInfo(kanji:)`, which refetches that kanji with the rejected story quoted so the model writes a different one, and overwrites the cache entry (spinner + inline error handled by `KanjiDetailView.regenerateMnemonic()`). Rerolls use `TranslationService.mnemonicRerollModel` (**`claude-fable-5`** — Mythos-class, above Opus): some Opus mnemonics are still weak, and a reroll is the user explicitly asking for better, so the single-kanji retry gets the top model (bulk fetches stay on Opus for cost). Fetched entries (and regenerations) are **shared through CloudKit with other devices and the kanji-study app** — a kanji either app has already fetched anywhere costs no new model call (see the kanji-info bullet under **iCloud sync**). Sheet layout leads with the glyph as the hero (mirroring `WordDefinitionView` leading with the word): centered `displayKanji` glyph + seen-count caption → info card (`cardChrome`: meanings → readings → JLPT → example → components → mnemonic + reroll button) → familiarity picker → lookup-links row → stroke order. Stroke data comes from `KanjiVGService.loadSVG(for:)`, which fetches from KanjiVG (`raw.githubusercontent.com/KanjiVG/kanjivg/master/kanji/{codepoint}.svg`) on first request and caches the SVG to the app's `cachesDirectory` for offline reuse. KanjiVG is CC BY-SA 3.0 and the attribution is shown inside `KanjiDetailView`.
- **Pick the radicals yourself, or write the mnemonic by hand (`MnemonicEditorView`).** "Edit mnemonic…" sits next to "New mnemonic" in `KanjiDetailView`'s info card and opens a sheet for that kanji. Candidate parts = **bundled KRADFILE decompositions** (`Krad.parts`) unioned with any part only the model listed (parsed out of `KanjiInfo.components`, which is `"<glyph> <keyword>"`); parts already in `components` start selected, and the candidate list resolves once in `.task` so a completed generate doesn't shuffle chips mid-session. Two routes out, **both of which pin the entry**: *Generate from selected parts* → `TranslationService.regenerateKanjiInfo(kanji:using:)`, which builds `componentInstruction(kanji:components:rejecting:)` — a **user-message suffix, not a `kanjiInfoSystemPrompt` change**, so there is nothing to mirror into the kanji-study app when this wording changes — telling the model to set `components` to exactly the chosen labels verbatim and build the story from only those, on `mnemonicRerollModel`; and a `TextEditor` + Save → `DefinitionCache.saveCustomMnemonic(_:components:for:)`, which stamps `fetchedAt = now`, sets `pinned`, and routes through `setKanjiInfo` so the persist + `markDirty` happen in one place. Because `DefinitionCache` is an actor with no observation, the sheet owns the `KanjiInfo` it edits and hands the stored copy back via an `onSave` closure so the card behind it updates. `KanjiInfo.components`/`mnemonic` became `var` for this.
  - **`KanjiInfo.pinned: Bool?`** is optional so the wire shape is unchanged for ordinary entries and older installs decode fine — and note this is a **deliberate exception to the "shape change ⇒ bump the cache filename" rule** below: absent means "not pinned", which is unambiguous, and bumping would throw away every cached mnemonic for no reason. The kanji-study app has the identical field and the identical merge rule, and both apps preserve `pinned` when they re-publish the shared slice, so **a pin set in either app holds in both**. Consequences: automatic prefetches can't touch pinned entries for free (the prefetcher re-checks the cache per kanji, and a pinned entry is by definition cached), "New mnemonic" on a pinned entry goes through a `confirmationDialog` first, and a **confirmed reroll deliberately unpins** — that is how the user gives up a pin they no longer want.
- **KRADFILE data (`Krad.swift`, `KradKeywords.swift`, `krad_decompositions.json`).** Converted once from EDRDG's `kradfile` + `kradfile2` (EUC-JP → UTF-8; the `kradzip.zip` bundle at `ftp.edrdg.org/pub/Nihongo/` has both) into a committed 423 KB JSON of 12,156 kanji over 253 distinct components. **`KradKeywords.displayGlyphs` matters:** KRADFILE draws components from JIS X 0208, which lacks many radical forms, so it substitutes a containing kanji (汁 for 氵, 艾 for 艹, 邦/阡 for right/left 阝 — 22 in all, per the table in EDRDG's `kradintro`). Showing the stand-in would put a character in the picker, and in the model's prompt, that isn't in the glyph at all — precisely the failure `kanjiInfoSystemPrompt` warns against — so `Krad.glyph`/`Krad.label` resolve it first. Both Swift files are **byte-identical to the kanji-study app's** apart from their header comments; that app's test target enforces the keyword-completeness invariant, so if the KRAD data is ever regenerated, verify it there and copy all three files across together. Attribution: EDRDG licence (CC BY-SA), shown at the foot of the mnemonic editor (same inline pattern as the KanjiVG credit) and in the README's Credits.
- **Pomodoro study timer (`StudySession`):** the "Start study" button at the bottom-right of the action row — visible once a sentence is parsed and definitions have loaded, hidden while a session is already running — instantiates a parameterless `StudySession` (`@MainActor @Observable`, `Identifiable`) and stores it in `ContentView.studySession`. There is no full-screen cover and no per-sentence content tied to the session; the pomodoro runs alongside the regular `ContentView` so the sentence, word/kanji modals, and Breakdown stay fully interactive while studying. A **single** 25-min work / 5-min break cycle runs (it does NOT loop into a new work block): a `Task` polls every 500ms against a wall-clock end date; when the work timer expires the session plays the chime and switches into break mode (orange `breakOverlay` rendered as a `ZStack` sibling above the main `VStack`, locking the UI until the 5-min break ends). When the **break** timer expires, `finishSession()` cancels the timer and sets `isFinished = true`; `ContentView` observes this via `.onChange(of: studySession?.isFinished)` and clears `studySession` (dismissing the pill + overlay). The Task is `[weak self]`-guarded so it self-terminates when the session deinits — no explicit `deinit` needed. **Chime:** `playChime(remaining:)` plays system sound `1005` (the longer "alarm" tone) `chimeRepeats` (3) times back-to-back via `AudioServicesPlaySystemSoundWithCompletion` completion-chaining so the tones don't overlap and the end-of-work block is hard to miss. System-sound volume tracks the device ringer/system volume and can't be boosted programmatically. While a session is active, `ContentView` adds two `topBarTrailing` toolbar items to the left of the existing stats/gear buttons: `PomodoroPill` (declared at the bottom of `ContentView.swift`) showing `timer`/`moon.fill` + `monospacedDigit` time with `.contentTransition(.numericText())`, and an `xmark.circle.fill` End Session button that fires `showingEndSessionConfirmation` → destructive "End session?" alert → `session.end()` + `studySession = nil`.
- **Familiarity levels (`FamiliarityStore`):** `@MainActor @Observable` singleton (`FamiliarityStore.shared`) tracking a three-tier self-rating per word and per kanji: `.unknown` (default, absent from dict), `.familiar` (stepping stone — purely informational, behaves the same as Unknown), `.known` (graduated — hides furigana). Two JSON files in `applicationSupportDirectory/NihongoPro/`: `word_familiarity.json` (`[String: Level]`, keyed by `Word.text`) and `kanji_familiarity.json` (`[String: Level]`, keyed by `String(Character)`). Loaded into memory in the init via the same `try? Data(contentsOf:)` + `try? JSONDecoder().decode(...)` pattern as `DefinitionCache`. Setting a level to `.unknown` removes the entry from the dict so files only grow with user-marked items. Writes are dispatched via `Task.detached` (atomic write) so the main thread never blocks. - **iCloud sync (`SyncCoordinator`):** the four progress stores (`FrequencyTracker`, `ActivityTracker`, `FamiliarityStore`, `SavedSentenceStore`) sync iPad ⇄ iPhone via **CloudKit** (private database, no server we run; requires the paid dev account's iCloud capability — entitlements in `NihongoPro.entitlements`, container `iCloud.com.terrydonaghe.NihongoPro`). **Per-device-slice model:** each install has a stable `deviceID` (`UserDefaults` `syncDeviceID`) and owns exactly **one** CKRecord (recordType `DeviceData`, recordName = deviceID) in the custom zone `NihongoProSync`, whose `payload` CKAsset is the JSON of this device's own contribution to every store (a `DeviceSnapshot`). Because no two devices write the same record there are **zero write conflicts**; the displayed values are the **merge** of all devices' snapshots:
  - **counters** (word/kanji frequencies, daily activity, sessions) → **sum** per key across devices, so a count is never lost even if both devices are used offline. Each store keeps `my…` (this device) + `remote: [deviceID: slice]` and exposes the merged total through its existing API.
  - **familiarity** → newest `modifiedAt` per key wins; `.unknown` is kept as a timestamped **tombstone** (not removed) so a clear out-ranks an older set on another device.
  - **saved sentences** → union by trimmed text; newest of `savedAt`/`deletedAt` wins; deletes write a **tombstone** so they don't resurrect.
  - **kanji info (shared cache)** → `DeviceSnapshot.kanjiInfo` (optional `[String: KanjiInfo]`, so records from older installs decode) publishes this device's entire kanji-info cache; incoming entries merge **straight into `DefinitionCache`** by newest `fetchedAt` per kanji (nil = legacy, loses to any stamped entry; ties keep local). A **union of content, not per-device slices** — no `*_remote.json`, no tombstones, record deletion doesn't remove adopted entries (they're regenerable cache, and the adopter republishes them on its next local fetch). This slice is **shared with the kanji-study app**, which participates in the same zone with its own device record — whichever app fetches a kanji first pays the one Opus call, and a "New mnemonic" regeneration (fresh `fetchedAt`) propagates everywhere. `applyRemoteKanjiInfo` deliberately does NOT `markDirty` (no upload ping-pong); only a genuine local fetch does. The merge rule itself lives in the pure `DefinitionCache.shouldAdopt(remote:over:)`: newest-`fetchedAt`-wins, **except that a `pinned` local entry only yields to a remote that is both newer and itself pinned** — see the mnemonic-editor bullet.
  - Transport is `CKSyncEngine` (manages the zone, change token, push subscription, retries, offline queue). Stores call `SyncCoordinator.shared.markDirty()` after a local mutation → the engine uploads this device's record; on fetch, `SyncCoordinator` decodes each remote `DeviceSnapshot` and routes slices to the stores via `applyRemoteSlice(deviceID:slice:)` (the `@MainActor @Observable` stores update the UI live; `FrequencyTracker` refreshes `StatsView` on next open since it's read via `snapshot()`). A diagnostics section in `SettingsView` ("iCloud Sync") reads `SyncStatus.shared` (`@MainActor @Observable`: `accountAvailable`, `isSyncing`, `lastSyncDate`, `lastError`, `remoteDeviceCount`) and offers a **Sync now** button (`SyncCoordinator.shared.syncNow()` forces fetch+push), plus shows this device's short id (`SyncCoordinator.shortDeviceID`) to match against CloudKit Dashboard. Sync events/errors are logged via `os.Logger` (subsystem `com.terrydonaghe.NihongoPro`, category `sync`). Engine state is persisted to `sync_engine_state.json`. Started once at launch from `NihongoProApp` (`.task { await SyncCoordinator.shared.start() }`); if iCloud is signed out the app works fully on local data and sync resumes on sign-in. Background push needs `UIBackgroundModes` = `remote-notification` (Info.plist) + `aps-environment` (entitlements). **On-disk:** each store now persists `*_slice.json` (this device) + `*_remote.json` (cached remote slices) and **migrates once** from the pre-sync files (`word_frequencies.json`, `daily_activity.json`, `word_familiarity.json`, `saved_sentences.json`, …) on first launch. **Not synced** (by choice): `DefinitionCache`'s **word**-definition half (regenerable, polysemy-guarded) and Keychain API keys (per-device) — the **kanji**-info half of `DefinitionCache` IS synced (see the kanji-info merge bullet above). **Before any TestFlight/App Store build, promote the CloudKit schema from Development → Production in the CloudKit Dashboard** (dev schema doesn't carry over).

Replay is implemented by `.id(animationKey)` on the view; bumping the key forces a fresh parse + `animator.play(strokes:)`.
- **Breakdown view:** a Breakdown button sits to the right of Translate. Tapping replaces the English translation with the Markdown breakdown rendered by `BreakdownView` (custom mini-renderer handling `#`/`##`/`###` headings, `-`/`*` bullets, paragraphs, and inline `**bold**` / `*italic*` via `AttributedString`) and **hides the Breakdown button itself** — the action is one-way for the current sentence. Tapping Translate (with the same or different input) resets `showingBreakdown` to false and brings the Breakdown button back. The Markdown is cached in `ContentView.breakdown` for the lifetime of the current translation.
- **Clear button:** a destructive-role `.bordered` Clear button sits on the bottom-left of the action row (a `Spacer()` separates it from Show translation/Breakdown on the right). `ContentView.clear()` cancels any pending `autoParseTask`, resets `inputText`, `words`, `englishTranslation`, `isTranslationRevealed`, `parsedInputText`, all error/breakdown/loading state, and calls `speechService.stop()` if audio is still playing. Disabled while a translation is in flight or when there is nothing to clear (empty input AND empty results AND no error).
- **Spoken Japanese (TTS):** `SpeechService` (NSObject `ObservableObject`, exposes `isSpeaking`) has **two playback engines**, selected by the `VoiceEngine` enum (`apple` / `azure`, declared in `SpeechService.swift`) and dispatched in a `switch` inside `speak(_:)`. The chosen engine is `SpeechService.voiceEngine` — reads UserDefaults `voiceEngine` (the Settings segmented picker), defaulting to `.apple`. The Azure engine falls back to Apple if its key or region is missing. (An ElevenLabs path existed previously and was removed entirely — Terry preferred the on-device voice to ElevenLabs and Azure to both; if you find references to it, they're stale.)
  - **On-device (default / offline):** `AVSpeechSynthesizer` for ja-JP. Voice selection respects a user-chosen `AVSpeechSynthesisVoice.identifier` stored in `UserDefaults` under `speechVoiceIdentifier`; empty/unset falls back to the highest-quality installed ja-JP voice (premium > enhanced > default).
  - **Premium (optional, Azure):** when the engine is `.azure` **and** both an Azure Speech key (`KeychainStore.read(account: .azure)`) and a region (UserDefaults `azureRegion`, e.g. `westus2`) are present, `speak(_:)` routes through `AzureSpeechService.synthesize(_:voiceName:style:apiKey:region:)` and plays the MP3 via `AVAudioPlayer`. Azure is the **correctness-oriented** premium engine: the voice is locked to a `ja-JP` neural voice (no language auto-detect → kanji never reads as Chinese) and the engine uses a real Japanese morphological dictionary, so common readings, the sokuon, and numbers are handled natively rather than guessed. REST: `POST https://{region}.tts.speech.microsoft.com/cognitiveservices/v1` with the text wrapped in minimal SSML (`<speak xmlns:mstts=…><voice name='…'>…</voice></speak>`, XML-escaped); headers `Ocp-Apim-Subscription-Key`, `Content-Type: application/ssml+xml`, `X-Microsoft-OutputFormat: audio-24khz-48kbitrate-mono-mp3`, and a **required** `User-Agent` (Azure rejects requests without one). No `<prosody rate>` in the SSML — playback rate is applied on the `AVAudioPlayer`, so cached MP3s stay rate-neutral. The voice ShortName is UserDefaults `azureVoiceName` (empty → `AzureSpeechService.defaultVoice`, `ja-JP-NanamiNeural`). Free tier covers 500K chars/month — effectively free for personal study.
  - **Azure speaking styles:** some ja-JP voices expose a `StyleList` (cheerful, newscast, chat…). The chosen style is UserDefaults `azureVoiceStyle` (empty = the voice's default delivery), read as `SpeechService.selectedAzureStyle` and threaded into `synthesize`'s `style:` param. A non-empty style wraps the text in `<mstts:express-as style='…'>` — which is why `<speak>` carries the `xmlns:mstts='https://www.w3.org/2001/mstts'` namespace. The Settings style `Picker` only renders when the selected voice has styles, and selecting a voice that lacks the current style resets `azureVoiceStyle` to "" so an invalid `express-as` is never sent.
  - **Shared machinery:** `isSpeaking` is set optimistically at fetch start (Azure path) so the stop control shows during the network round-trip; `stop()` cancels the in-flight `fetchTask` and stops both the synthesizer and the player. **Any** Azure failure (offline, bad key/region, quota, decode) falls back to the on-device voice via `fallBackToApple(_:)` — the app always speaks something. Fetched MP3s are cached under `cachesDirectory/AzureAudio/<sha256(key)>.mp3` via the generic `cachedAudio(key:subdir:fetch:)` + `cacheURL(key:subdir:)` helpers (Azure key `azure|region|voice|style|text`). So replays and previously-heard saved sentences play offline, and changing the region/voice/style re-fetches rather than serving stale audio.
  - **Voice selection (Azure):** the Settings picker lists the region's ja-JP neural voices via `AzureSpeechService.fetchJapaneseVoices(apiKey:region:)` (`GET /cognitiveservices/voices/list`, filtered to `Locale == "ja-JP"`, sorted by display name). Each row is tap-to-select (storing its `ShortName` in `azureVoiceName`) and shows its supported styles inline (tint `.caption2` line) so it's clear which voices offer styles; there's no per-voice free sample (Azure's voice list carries no preview URL), so auditioning is via the shared Play Sample button with the engine set to Azure. **Note:** styles are sparse and region-dependent — e.g. in `westus2` only plain `ja-JP-NanamiNeural` (chat/customerservice/cheerful) has a non-empty `StyleList`; the newer HD/Dragon and MAI voices return none and don't accept `express-as`.
  - **Sentence vs single-word speech input:** the two contexts feed different text on purpose. The core problem: feeding the engine raw **kanji** sounds natural but can mis-read rare compounds (精米歩合 → "seimebukara"); feeding pure **kana** reads correctly but flat/robotic. The solution is **selective kana substitution**, using the `tts_kana` flag from pass 1.
    - **Full sentence** (`ContentView.translate()` auto-play and the replay speaker button both speak `words.sentenceSpeechText()` — the `[Word]` extension in `TranslationService.swift`): each word is spoken as its **kanji surface form** unless `ttsKana == true`, in which case it's swapped to its **kana reading**. So a sentence stays mostly natural kanji (good prosody) with only the tricky words (e.g. 精米歩合 → せいまいぶあい) converted.
    - **Arabic digits are deliberately left as-is (do NOT re-add digit→kana conversion).** This was tried and reverted on the old ElevenLabs path: converting digits to their kana reading fixed correctness but **wrecked prosody** (the injected kana island gets phrased as its own chunk, inserting pauses in the wrong places), and a normalizer fed raw digits mis-read them / leaked its reasoning into the audio. Terry chose **natural prosody over number correctness**. With Azure's real dictionary, numbers generally read correctly anyway. If this resurfaces, the lever is *not* text munging.
    - **Single word** (`WordDefinitionView` per-word button speaks `[word].sentenceSpeechText()` — i.e. the *same* selection rule as a one-word sentence): the **kanji surface form** unless `ttsKana == true`, in which case the kana reading. This was changed from always-kana after a by-ear finding (on the old premium path): feeding bare kana could **truncate a terminal っ/つ** (温帯低気圧 → "…おんたいていきあ"), while the kanji read correctly. Preferring kanji fixed it; the rare-compound case (精米歩合) is still covered because those words are `ttsKana`-flagged and so still drop to kana. (`StatsView` builds a minimal `Word` with `reading == text` and `ttsKana == nil`, so its word playback feeds the surface form — unchanged.)
  - **Auto-read toggle:** whether the sentence is read aloud automatically when a parse lands is a setting — `@AppStorage("autoReadAloud")`, **off by default** — a "Read sentence aloud automatically" `Toggle` in the Voice Engine section of `SettingsView`, gating the `speechService.speak(...)` call in `ContentView.translate()`. When on, playback fires **after** the Claude response lands (so the audio is synchronized with the visual reveal of the furigana — never before the render). When off (default), the sentence is silent until the user taps the speaker button. The speaker/stop button in the Japanese display area works regardless. Failed requests do not play audio. **Rate** (Natural / 85% / 65%, key `speechRate`) applies to both engines: as the `AVSpeechUtterance.rate` multiplier on the Apple path and as `AVAudioPlayer.rate` (`enableRate = true`) on the Azure path. The Settings sheet has a **Voice Engine** section (segmented On-device/Azure picker + Rate + auto-read toggle + Play Sample, which exercises whichever engine is active), an **On-device Voice** section (every installed ja-JP Apple voice), and a **Premium Voice (Azure)** section (key + region + voice list + style picker).
- **API key storage:** iOS Keychain (`kSecClassGenericPassword`, service `com.terrydonaghe.NihongoPro`). `KeychainStore` is keyed by a `KeychainStore.Account` enum — `.anthropic` (`anthropic-api-key`, the default for all `read/save/delete`), `.openai` (`openai-api-key`, the ChatGPT provider key), `.azure` (`azure-speech-key`, optional premium voice), and `.videoStudySync` (the Video-Study relay shared secret — see the **Video-Study sync** note). The three AI/speech keys are all entered in-app via `SettingsView` (Anthropic on first launch, OpenAI in its own key section below the AI Provider picker, Azure in the Premium Voice section); re-openable via gear icon. The OpenAI key uses an in-section Save/Update + destructive Remove button (mirroring the Azure section) rather than the bottom-toolbar Save button, so the first-launch dismiss-gating (which still keys on the Anthropic key via `hasExistingKey`) is untouched. The Azure **region** is not secret and lives in UserDefaults `azureRegion`, not the Keychain. No xcconfig/Secrets file.
- **Dependencies:** none third-party (no SPM, no CocoaPods). System frameworks only: Foundation, SwiftUI, Security (Keychain), AVFoundation (TTS + `AVAudioPlayer`), CryptoKit (audio-cache hashing), CloudKit (iCloud sync via `CKSyncEngine`). Network data: the AI provider (Anthropic Messages API or OpenAI Chat Completions API, per the **AI provider switch**), KanjiVG (CC BY-SA 3.0, fetched on demand), and — only when the user opts in with their own key — the Azure Speech TTS API. iCloud (CloudKit) syncs progress across the user's devices using Apple's infrastructure (no server we run).
- **Trigger:** debounced auto-parse on `inputText` change (800ms). Translation reveal is gated behind the **Show translation** button so the user can attempt to read the sentence first.
- **Device target:** universal — iPad + iPhone (`TARGETED_DEVICE_FAMILY = "1,2"`), iPadOS / iOS 26+ (`IPHONEOS_DEPLOYMENT_TARGET = 26.0`). iPhone is portrait-only; see **iPhone adaptation** above for the idiom-gated layout differences.
- **Bundle ID:** `com.terrydonaghe.NihongoPro`.

## Build & run

Open `NihongoPro.xcodeproj` in Xcode and Run on an iPad simulator. Headless build for verification:

```bash
xcodebuild -project NihongoPro.xcodeproj -scheme NihongoPro \
  -destination 'generic/platform=iOS Simulator' \
  -configuration Debug build CODE_SIGNING_ALLOWED=NO
```

Always run this after editing Swift files or pbxproj — SourceKit diagnostics shown during edits are noisy and unreliable; the actual build is the source of truth.

## Adding a new Swift source file

The pbxproj uses readable sequential IDs of the form `FA00000000000000000000{XY}`. When adding `NewFile.swift`:

1. Pick the next unused suffix (e.g. `A9` for the file ref, `B9` for the build file).
2. Add a `PBXFileReference` line in the PBXFileReference section.
3. Add a `PBXBuildFile` line in the PBXBuildFile section.
4. Add the file ref `A9` to the `FA00000000000000000000D1 /* NihongoPro */` group's `children`.
5. Add the build file `B9` to the `FA00000000000000000000E1 /* Sources */` build phase's `files`.
6. Rebuild with the xcodebuild command above.

## Tuning behavior

- **Translation/furigana quality:** edit `translationSystemPrompt` in `TranslationService.swift` (pass 1). This prompt also owns the `tts_kana` per-word flag that drives selective kana substitution for speech — if rare words are mispronounced (flag missed) or speech sounds flat (over-flagging), tune the `tts_kana` guidance/example there. Definition quality lives in `definitionsSystemPrompt` (pass 2). Breakdown depth and structure live in `breakdownSystemPrompt`. Per-kanji info shape lives in `kanjiInfoSystemPrompt` (the `jlpt` level field, the `components`/`mnemonic`/`example` study aids, and the bad-vs-good 展 mnemonic example — it's the **same batch prompt** as kanji-study's `KanjiInfoService.systemPrompt`, so mirror any guidance change both ways; a shape change to `KanjiInfo` means bumping the kanji cache filename again, see the DefinitionCache note — **except for a purely additive optional field like `pinned`**, which must NOT bump it). Note `effort: "high"` is the API **default**, not an elevated setting — the scale is low/medium/high/xhigh/max, so `xhigh` is available if rerolls ever want more depth. **`kanjiInfoMaxTokens` (32000) covers thinking AND the answer:** at the old 16000 a constrained reroll could spend the whole budget deliberating and be truncated before emitting text, which reached the UI as a bogus "couldn't parse the JSON". `sendMessage`/`sendKanjiInfoMessage` now guard on empty text and throw `TranslationError.emptyResponse(stopReason:detail:)`, decoded from `stop_reason` plus a one-line rendering of `stop_details` (refusal `category`, `explanation`, `recommended_model` — `MessagesResponse.StopDetails.summary`), so a truncation and a `refusal` (also 200-with-no-text) report themselves distinctly and a refusal says *why* in the banner. `fetchKanjiInfoBatch` retries once on it — **on the same model for `max_tokens`** (transient; thinking length varies), but **on `kanjiInfoModel` (Opus 5) when a Fable reroll was refused**: the classifier is deterministic on the input, so re-asking Fable just refuses again (which is what happened on a benign 圏 reroll — the server-side `fallbacks: "default"` didn't rescue it, some categories fall back to nothing), and Opus 5's classifiers cover fewer categories. Each empty response is also logged (`os.Logger` category `ai`) with the stop reason and details. Raising the cap is free — billing is per token generated, and a truncated request billed for the thinking and returned nothing. The hand-picked-parts wording is `TranslationService.componentInstruction`, a user-message suffix rather than a system-prompt change, so it needs no mirroring; candidate parts and their keywords come from `KradKeywords`, so add or reword entries there rather than post-processing what the model returns. Keep the worked example in each prompt — they reliably anchor Claude's output shape (JSON for passes 1/2/kanji, Markdown for breakdown).
- **Stroke order animation:** `KanjiStrokeView` is fully native SwiftUI (see Tap-to-explore-kanji above for the render pipeline). To tune the look: stroke thickness, completed-stroke opacity, badge size, and grid/dash colors all live in `StrokeCanvas` inside `KanjiStrokeView.swift`. Per-stroke duration scaling lives in `StrokeAnimator.duration(for:)`. Replay is implemented by bumping `KanjiDetailView.animationKey` which `.id()`-keys the `KanjiStrokeView` — SwiftUI discards and recreates the view, which re-parses the SVG (cheap, ~ms) and starts a fresh `animator.play(strokes:)`. Cache directory for fetched SVGs is `FileManager.default.urls(for: .cachesDirectory, ...)` so files may be evicted under disk pressure; refetch is automatic.
- **Furigana display:** `FuriganaText` view exposes `showFurigana`, `drillMode`, `baseFont`, `rubyFont`, `rubyColor`, `wordSpacing`, `lineSpacing`, and `onWordTap` parameters. Outside drill mode, each word is wrapped in a `Button` and disabled when `definition == nil` (punctuation). Both word buttons (normal + drill) use `WordTapStyle` — a private `ButtonStyle` (0.96 scale + 0.7 opacity while pressed) that replaces `.plain` for touch feedback; drill reveals animate via `withAnimation(.smooth(duration: 0.2))` around the `revealedIndices` toggle. Tappable words get a 3pt underline via a bottom overlay inside `WordView` (now driven by the explicit `underline:` parameter) — colored by word familiarity (`KnownGreen` / `LearningYellow`), falling back to `.tint` for Unknown; punctuation gets no underline. Kanji glyphs are tinted per-character by kanji familiarity (see the **Knowledge markup** architecture note; tune colors in the `KnownGreen`/`LearningYellow` assets or the `markupColor` mapping in `Theme.swift`). In drill mode (`drillMode == true`) the tap toggles per-word reading reveal instead — see the **Reading drill mode** architecture note. The flow-wrap logic is `FuriganaFlowLayout` in the same file. Note: wrapping words in `Button` removes per-character text selection on the Japanese display in exchange for tap-to-define; the English translation below remains selectable.
- **Definition sheet:** `WordDefinitionView` is a small SwiftUI view shown via `.sheet(item:)` with `.presentationDetents([.medium, .large])`. The selection state lives in `ContentView.selectedWord: WordSelection?` (a UUID-id wrapper around `Word` so `.sheet(item:)` works even when the same word appears twice). The sheet receives the shared `SpeechService` via init (`@ObservedObject`) so its play/stop button reflects the same `isSpeaking` state as the main display — closing the sheet while audio is still playing does not stop it.
- **TTS tuning:** voice selection priority is in `SpeechService.selectedVoice()` (UserDefaults override → `bestJapaneseVoice()` fallback). Quality-tier fallback is in `bestJapaneseVoice()` / `availableJapaneseVoices()` — change the sort order to change auto-pick behavior. Rate multipliers are in `SpeechRate.multiplier`. Audio session is **idiom-gated**: on **iPhone** it's `.playback` so the ring/silent switch can't mute study audio; on **iPad** it stays `.ambient` (unchanged — iPad has no hardware mute switch). The Azure path sets the category in `startPlayback(_:)` (`Self.isPhone ? .playback : .ambient`, then `setActive(true)`); the Apple path calls `activatePlaybackSessionForPhone()` first, which sets `.playback` **only on iPhone** and is a no-op on iPad (so the iPad Apple path keeps its historical default session). `Self.isPhone` is `UIDevice.current.userInterfaceIdiom == .phone` (SpeechService imports UIKit for this). To make iPad always play too, drop the gate and use `.playback` everywhere. `SettingsView` reads `SpeechService.availableJapaneseVoices()` to populate its Voice picker — `SettingsView` takes the live `SpeechService` instance via init so the Play Sample button shares state with the main display. The engine routing decision is the `switch Self.voiceEngine` at the top of `SpeechService.speak(_:)` (the Azure branch also checks its Keychain key + region, falling back to Apple); the fallback-on-error path is `fallBackToApple(_:)`.
- **Premium voice (Azure) tuning:** the fallback voice is `AzureSpeechService.defaultVoice` (`ja-JP-NanamiNeural`); the request shape (SSML body with optional `<mstts:express-as>` style wrapper, `audio-24khz-48kbitrate-mono-mp3` output format, the **required** `User-Agent` header, the region-scoped host) lives in `AzureSpeechService.synthesize`. The voice list is `AzureSpeechService.fetchJapaneseVoices` — it hits the region's `/cognitiveservices/voices/list` and filters `Locale == "ja-JP"`; the picker stores the chosen `ShortName` in UserDefaults `azureVoiceName`. **Styles:** the picker reads the selected voice's `StyleList` and writes the chosen style to UserDefaults `azureVoiceStyle` (empty = default delivery); it's read as `SpeechService.selectedAzureStyle` and only emitted as `<mstts:express-as style='…'>` when non-empty (which is why `<speak>` carries the `mstts` namespace). To widen what styles appear, nothing to tune — they come straight from Azure's per-voice `StyleList`. Rate is applied on the `AVAudioPlayer` (no `<prosody>` in SSML), so cached MP3s are rate-neutral; the cache is subdir `AzureAudio`, key `azure|region|voice|style|text` (bump any component to invalidate). Any error → `fallBackToApple`, same idiom-gated audio session (`.playback` on iPhone, `.ambient` on iPad — see TTS tuning above). Azure has a real Japanese dictionary so it's the most reliable engine for readings/sokuon/numbers — if a *specific* word still mis-reads, the SSML lever is a `<phoneme>` tag or a custom lexicon (both genuinely supported for Japanese), added in `AzureSpeechService.synthesize`. If `fetchJapaneseVoices` returns empty, the region likely doesn't offer ja-JP voices (rare) or the region string is wrong — both surface as the "Couldn't load voices" error in Settings.
- **Input validation:** `ContentView.maxInputLength` (200 characters, trimmed) caps the input; over it, auto-parse is blocked and an inline orange warning below the text editor shows the current count. From `counterRevealThreshold` (150) up to the cap, a quiet tertiary `N / 200` counter (`.numericText()` transition) shows below the editor so the hard cap is never a surprise; the over-limit warning replaces it past the cap. Multiple sentences within the budget are fine — the cap is sized for a manga speech bubble or a few short sentences (MangaAssist's tap-a-bubble handoff sends exactly that via `nihongopro://lookup?text=…` → `ContentView.handleIncomingURL`). This replaced the old one-sentence rule (`isMultiSentence(_:)`, ICU `.bySentences` counting), which mis-fired on manga text: a 20-char bubble of four exclamations was blocked while one 150-char sentence passed, and length — not sentence count — is what actually strains the parse (word-entry JSON grows linearly with input).
- **Model:** `TranslationService.model` (Claude) and `TranslationService.openAIModel` (ChatGPT) constants. Sonnet 4.6 is the chosen Claude balance; Haiku is cheaper but weaker on idiomatic readings, Opus is overkill for sentence-level. Kanji info is separate: `TranslationService.kanjiInfoModel` (`claude-opus-5`, high effort, always Anthropic — see **Tap-to-explore-kanji**), with "New mnemonic" rerolls on `mnemonicRerollModel` (`claude-fable-5`); latency knobs there are `kanjiInfoTimeout` and the effort in `KanjiInfoMessagesRequest` (Terry doesn't want the effort lowered). `gpt-4.1` is the ChatGPT default — the tier match to Sonnet that keeps the classic Chat-Completions request shape; changing it to a GPT-5/o-series reasoning model means swapping `max_tokens` → `max_completion_tokens` and dropping custom temperature in `sendOpenAIMessage`. Which model runs depends on the **AI provider switch** (`aiProvider` in UserDefaults / the Settings picker).
